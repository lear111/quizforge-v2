# 原型评审发现的接口缺口与文档矛盾

依据：`docs/design-ui-inventory` @ `ecc571b`。这里只记录，不更改 `docs/`；下方单列用户在评审中确认的覆盖项。

| 编号 | 缺口或矛盾 | 原型处理 / 建议评审的问题 |
| --- | --- | --- |
| G-01 | `05` 和共享规则要求公开版 + 待审核版并存，但 `GET /api/packs`、详情、PUT 的字段级结构未定义。旧接口的单个 `version/revision/status` 无法可靠同时表达两个版本。 | 用“公开 1.2 / 审核中 1.3”假数据演示。需确定 approved / pending DTO、作者编辑视图与匿名可见信息，不能让待审文件泄漏成公开附件。 |
| G-02 | 原设计要求列表显示更新状态、当前/目标版本与进度，API 只承诺目录列表。当前原型按评审取消待更新提示，但移除标记与进度仍需要目录字段。更新检查却只在打开概览时进行；只返回实例 `update_status` 会使“我的题库”标记滞后。`update.revision` 也没有明确展示版本名。 | 不发 N+1 请求或在前端检查版本。建议明确目录聚合字段与更新时间口径，区分包版本整数和显示版本字符串；`removed` 与 status 枚举需统一。 |
| G-03 | 按本加入采用 `bank_key`，但旧目录返回 `id`，新 POST 的响应没有定义。无法确认多本加入后定位哪一本、如何返回已有实例、并发时的行为，以及如何在点击前显示“已加入”。 | checkbox 保存完整 bank_key；确认后跳到固定列表，不创建假实例。需定义每个 bank_key 对应的 collectionId/是否已存在；若加入前无此字段，可只在 POST 后反馈，避免虚构查询接口。 |
| G-04 | 单题返回 `updatedByAuthor:true` 已写入共享设计，API 总表没列字段；概览/大纲要标记已更新题，但未定义相应列表字段。标记是否持久、何时清除也未定。 | 展示“更新”文字与条幅；不实现“已读确认”。需要概览逐题标志，避免读完全部题才画大纲；确认字段/清除语义。 |
| G-05 | “立即更新”只定义 `{requestId}`，未定义确认对话框与目标版本的绑定、响应是否返回中断历史 ID。共享规则 3.1 把进行中/评分中考试也归为暂缓，却只解释了如何中断练习轮次；3.3 又说考试结束后才更新。 | 用户已要求取消手动更新界面，原型不再演示立即更新。该接口若仍保留，需明确考试期间立即更新是否允许、冻结考试与所属实例的关系；若确认期间作者又发布新版，如何防止与用户确认的版本不一致。 |
| G-06 | 汇总/完成/历史沿用旧语义，但缺字段级 DTO：已提交题满分 vs 全库满分、待评分计数/可完成、耗时、历史版本、中断原因、finish 后的更新结果。 | 得分明确写“已提交题目得分 / 已提交题目满分”；待评分禁用完成。旧版历史与当前新版分开展示，不从当前题目重新拼历史。 |
| G-07 | AI 端点尚未定义权威状态快照、重做次数、对话消息结构/短期时长、首次恢复 conversationId、流事件及错误码/计费重试。2.5 写 SSE，但 API-1 又将 SSE/轮询列为待定。 | 只演示固定对话与异常；切题更换 fixture，不调用模型，不主动暴露未提交答案。需要正式事件/恢复/错误与额度契约。 |
| G-08 | 额度接口沿用旧 Java Hub，但本文 API 没有 balance 的单位/显示精度、可用状态、额度不足错误及兑换字段。 | 原型 ¥12.48 为合成显示值，不是 token 数。需沿用并记录旧金额换算口径，不能把数据库整数直接显示为元。 |
| G-09 | “更新说明”仍是 UP-2 待定项；上传 schema、版本说明存储/返回位置没定义。旧上传文案曾有编辑暂停公开的规则，与新规则不同。 | 按 UI 清单展示可选字段，固定提示旧公开版本继续可用；不提交或要求后端接受自创 changeNote 字段。 |
| G-10 | 需求文件当前仍是 v1.0，只有 FR-01～FR-08；多份设计引用 FR-09、FR-10、需求 v1.1，无法在指定需求文件定位这些条款。API 页眉 v0.1 与变更记录 v0.2 也不一致。 | 明确按 UI 清单及共享设计完成原型，不伪造 FR-10 原文。建议主文档维护者同步需求和版本头；本 PR 不改 docs。 |
| G-11 | UI 清单要求 503 显示“正在重试”，API 只定义失败码，未明确何种动作可重试、期限、退避、幂等键/版本冲突处理，以及输入保留范围。 | 静态显示待重试与恢复两种状态，既不定时重试也不假装可靠保存；“保留输入”仅指当前页面，不承诺刷新后恢复。 |
| G-12 | UI-2 仍待定是底部抽屉还是全屏；UI-3 是否提供更新前作答入口也待定。 | 手机按 2.4 节展示可关闭的底部抽屉；不在更新条幅增加未经决定的旧作答入口。中断/完成的历史只在既有历史弹窗中展示。 |
| G-13 | 设计分支尚未合入 main；main 只有初始需求等文档。若从设计分支直接开 PR 会把 16 份设计文件也带进去，违反此次只增加原型的边界。 | 原型从 main 新建分支，PR 只含 prototypes；使用固定设计提交链接。设计文档合并由其独立 PR 处理。 |

另外，API 文档的 `{revision, contentVersion, requestId}` 是后端写入一致性字段，不是前端展示的题库版本号。原型不将这些字段混用，也不实现原本应由服务端完成的哈希比较、合并、权限或评分。

## 用户评审覆盖项（2026-10-27）

1. UI 清单原要求“有新版本”和立即更新确认；用户明确移除，原型改为自动更新后的状态，不给普通用户手动更新入口。接口可继续存在，但本原型不暴露。
2. 用户要求直接复用旧前端。第 03 组只展示原有左侧列表，不增加独立“我的题库”主页面；统一入口为练习空间。
3. AI 与大纲共用一个区域，标签切换；桌面调宽、手机抽屉调高，保留题区空间。UI-2 的原选择因此采用共用抽屉方案。
4. 这些指示只体现在 prototypes，未擅自修订 docs。PR 应由设计维护者核对并更新对应文档。
