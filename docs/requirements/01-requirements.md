# QuizForge V2 需求规格说明书

> **文档版本：** v1.0（初始需求基线）  
> **状态：** 需求范围已确认；技术方案与细节仍待设计评审  
> **日期：** 2026-10-27  
> **维护仓库：** lear111/quizforge-v2  
> **当前阶段：** 需求分析完成，准备进入现有系统架构分析

## 1. 背景与项目目标

QuizForge 已具备题库发布与管理（Hub）、本地 Web 题库编辑、题型拓展、在线练习、答案保存、考试和历史记录等功能。现有云端练习实现复用了原先面向本地单用户的运行模式，尚未针对多用户并发进行系统性的架构规划。

本次 QuizForge V2 重构面向 **在线 Web 多用户刷题平台**，目标是建立职责明确、可维护、可验证、可演进的工程架构，并在约定的生产级测试环境中达到 **至少 100 名活跃用户同时刷题** 的能力。

重构应优先复用经过验证的业务规则、题库数据格式与题型拓展能力，不以全面重写为目标，也不以引入微服务、Redis 或消息队列等特定技术作为需求目标。

### 1.1 产品边界

| 产品/系统 | 定位 | 本次 V2 范围 |
| --- | --- | --- |
| QuizForge V2 Web | 面向普通用户的在线题库、练习与 AI 辅导平台 | **本次重构的交付主体**，承担 100 人并发目标 |
| QuizForge Hub | 题库发布、浏览、管理与在线平台业务入口 | 作为 V2 在线平台的一部分纳入需求 |
| 现有 Windows / 本地 Web | 本地刷题、题库制作、编辑、调试、新题型预览 | **继续维护的关联产品**，不纳入 V2 云端并发指标 |
| 题型拓展（插件） | 独立题目渲染与题型专属交互逻辑 | 保留独立性；V2 需要兼容和管理其运行能力 |

V2 第一阶段不开发新的 Windows/Android 原生客户端，也不将本地部署、局域网连接或离线优先同步作为在线平台的交付任务。**这不代表停止维护现有 Windows / 本地 Web 产品。**

### 1.2 核心业务链路

1. 用户访问在线网站并完成身份认证。
2. 用户浏览题库，选择题库并导入个人练习空间。
3. 用户进入练习空间，加载题目及其所需资源。
4. 对应题型拓展在独立页面中渲染题目并处理作答交互。
5. 用户保存草稿、提交答案、重做题目或参加考试；宿主负责统一业务控制和数据保存。
6. 用户查看反馈、评分及历史记录，并可针对当前题目向 AI 助手提问。
7. 题库开发者可在 Windows / 本地 Web 中编辑和验证题库，再通过 Hub 上传和发布。

## 2. 功能需求

### FR-01 用户身份与访问控制

- 支持用户注册、登录、退出和必要的账号管理。
- 不同用户的私人题库、练习状态、答案、草稿及历史数据相互隔离。
- 服务端统一执行身份认证与资源访问权限校验；不可仅依赖前端隐藏按钮。
- 支持题库发布者与平台管理者执行其授权范围内的管理操作。

### FR-02 Hub 题库管理

- 支持题库浏览、检索、详情查看、发布、编辑、管理与下架。
- 支持将可使用的题库导入个人在线练习空间。
- 保留适用的题库审核及管理功能。
- 不因 V2 重构破坏已有题库数据和必要的使用流程。
- 题库上传与发布时，应能够判断题库所需能力是否被当前在线练习环境支持（见 FR-07）。

### FR-03 个人云端练习空间

- 用户能够查看、打开和管理个人练习题库。
- 支持题目加载、题目切换、作答、草稿及答案保存、提交与评分。
- 支持重新作答、历史记录、考试/试卷练习，以及现有适用的手写/草稿能力。
- 页面刷新或重新登录后，能够恢复已经成功持久化的练习状态。
- 保留既有题型规则、评分语义、历史数据及必要的题库格式兼容性。
- 系统应能清晰区分「尚未作答」「作答中」「题目已提交/已评分」「整轮练习已完成」等状态。

### FR-04 多用户并发与写入一致性

- 至少 100 名活跃用户可在同一时段执行真实混合练习操作。
- 不同用户的普通读写请求不得因不必要的全局串行机制长期相互阻塞。
- 同一题目或练习状态发生并发修改时，必须有明确的一致性规则，避免静默覆盖。
- 保存成功的确认应以服务端可靠持久化为依据；失败和状态不明确时，应向用户提供可理解的反馈。
- 服务器异常后，应能够恢复已确认保存的数据，且不得出现跨用户数据串扰。

### FR-05 题型拓展系统（独立核心子系统）

QuizForge 的题型拓展不是宿主页面内部的普通组件，而是**嵌入练习空间的独立页面**。现有使用 iframe 与宿主通信的模式应作为设计基础予以保留。

- 拓展独立承担题目渲染及题型专属的交互逻辑；宿主不必了解每一种题型的具体界面实现。
- 拓展与宿主通过**明确、版本化的 Bridge API/消息协议**通信，而非任意直接访问彼此内部状态。
- 至少覆盖题目初始化、作答数据读取/回填、草稿保存请求、正式提交请求、状态变化通知及操作结果返回。
- 例如：拓展页面中的「提交」按钮发出标准化事件，宿主验证当前用户与题目上下文，调用后端执行保存或提交业务，再将结果传回拓展。
- 应明确区分「保存草稿」与「正式提交/评分」，避免业务语义混淆。
- 用户身份、数据权限、可靠持久化及可信评分结果由平台后端掌控，不能只信任插件前端提供的结果。
- 题型拓展具备明确的运行安全边界；不得借插件接口绕过平台权限。
- 新题型应尽量通过扩展协议和插件实现接入，避免反复修改练习平台核心业务代码。
- 既有插件能力和数据协议应优先保留；变更必须考虑版本兼容与迁移。

### FR-06 平台托管资源服务

资源能力不限定于听力文件，应支持音频、视频、图片、PDF 和未来新增的静态附件类型。

- **由 QuizForge 管理的服务器或存储服务实际托管的文件**，属于平台的性能与可用性保障范围。
- 用户上传题库后，纳入平台托管的题库附件同样适用该要求。
- 应支持不少于 100 名活跃用户并发访问平台托管资源，并与题目读取、答案保存等动态业务适度解耦。
- 支持合理的缓存策略，并在适用时支持 HTTP Range 分段请求。
- 必须保留资源访问权限控制，不因缓存或静态服务优化泄露非公开资源。
- 传输能力的验收须结合文件大小、并发请求数和实际服务器出口带宽进行测试。

### FR-07 外部资源与题库版本兼容

- 题库可按既定协议引用外部 URL 资源。
- **外部 URL 所指第三方服务器的速度、带宽、稳定性和持续可用性不属于 QuizForge 性能承诺范围。**
- 平台仍需处理外部资源加载失败、超时与安全风险。
- Windows / 本地 Web 版本可**先于在线 Web 版本**实现和发布新题型、新功能。
- 题库格式与拓展协议应具备明确的版本号或能力声明，供 Hub 和在线练习环境进行兼容性检查。
- Hub 可以接收待完善或待适配的题库，但不得向普通用户提供无法被在线环境正确运行的已发布题库。
- 本地与在线版本应遵循一致的题库核心协议；不强制二者使用相同的后端运行方式或存储实现。

### FR-08 基础 AI 题目辅导助手

V2 第一阶段提供**基于当前题目与实时练习状态的问答辅导**，可采用练习页面侧边栏形式。

- 用户进入或切换题目后，AI 问答能够关联当前题目的题干、选项、题型及必要的题目材料。
- AI 可获知用户此时是否正在答题、当前题目是否已提交/评分、整轮练习是否完成。
- AI 可获知当前题目的重做次数，并据此适度调整讲解方式。
- 练习系统是作答状态、重做次数和评分结果的权威数据来源；模型不自行推测这些事实。
- 未提交时默认采取引导式辅导，不主动暴露标准答案；已评分时可结合用户作答、标准答案及评分结果讲解。
- 支持当前题目的连续追问；切换题目时应正确更新上下文，防止串题。
- 优先采用用户主动提问触发模型调用；普通切题或保存不依赖 AI 响应。
- AI 调用需有身份校验、额度/频率限制、超时、失败处理和适当的数据访问控制。
- AI 发生错误或超时不得影响普通刷题、草稿保存和提交。
- AI 服务能力须独立评估；**100 人同时刷题不等于承诺 100 个大模型请求同时执行。**

第一阶段**不包括**：文件生成题库、自动修改/扩展题库、全局学习能力分析、个性化学习计划、跨题目长期记忆及复杂多 Agent 编排。

## 3. 非功能需求

以下为**待压测验证的验收目标**，不是对当前系统的性能宣称。

| 编号 | 维度 | 第一阶段目标 |
| --- | --- | --- |
| NFR-01 | 活跃用户 | 在同一套明确配置的测试环境下，至少 100 名活跃用户持续进行混合练习 |
| NFR-02 | 题目读取 | 关键读取 API 的 P95 响应时间不超过 500 ms |
| NFR-03 | 答案保存 | 关键保存 API 的 P95 响应时间不超过 1,000 ms |
| NFR-04 | 服务错误 | 约定压测场景中关键练习 API 的 5xx 错误率不超过 0.1% |
| NFR-05 | 数据可靠性 | 已明确确认持久化的作答数据丢失次数为 0 |
| NFR-06 | 数据隔离 | 不允许任何用户之间的私人练习数据串扰或越权访问 |
| NFR-07 | 托管资源 | 验证 100 名活跃用户同时请求/播放平台托管的混合静态资源 |
| NFR-08 | 稳定性 | 进行至少 30 分钟的持续混合负载测试，不出现不可控队列积压或资源耗尽 |
| NFR-09 | 客户端体验 | 重点验证真实浏览器切题、插件初始化、页面加载及输入反馈；另行制定前端性能指标 |
| NFR-10 | 可维护性 | 核心模块职责与 API 契约明确，关键业务具备回归测试和可追踪变更记录 |
| NFR-11 | 可运维性 | 具备部署配置、日志监控、备份、恢复、数据库迁移与回滚方案 |

**指标口径说明：**

- 「100 名活跃用户」指模拟真实练习节奏的并发会话，包括切题、读取、草稿保存、提交、查看历史及部分静态资源请求，不等同于 100 个静置登录会话，也不等同于同一毫秒发生 100 次写入。
- P95 指指定测量窗口内至少 95% 请求的响应时间不超过目标值；须同时记录 P99、吞吐量和错误率。
- API 延迟与浏览器端到端加载时间分别测量；网络条件、题库大小、缓存冷热及服务器规格均须记录。
- 平台托管资源的下载时间受资源体积及带宽制约，正式验收须固定测试资源组合、请求模式和带宽条件；不对任意大文件承诺统一毫秒级完成时间。
- 外部 URL 的第三方传输性能排除在资源并发验收之外。
- AI 的模型响应速度、费用与外部模型容量独立记录，不应与核心练习 API 的 SLA 混算。

## 4. 安全与质量约束

- 所有敏感操作必须由后端验证用户身份、租户/用户归属和访问权限。
- 题型插件、文件上传、外部资源引用和题库内容应符合安全边界设计；不得将不可信的插件代码视为受信任的后端逻辑。
- 个人答案、历史记录、题库权限和 AI 上下文不得跨用户泄漏。
- 重构过程应保护已有题库、作答、考试与历史数据；迁移应具有校验、备份和回退手段。
- 采用可复现的开发、测试、部署流程，重要架构选型保留决策记录（ADR）。

## 5. 第一阶段明确不做

- 在 V2 仓库中重新开发 Windows/Android 原生客户端。
- 重构现有 Windows / 本地 Web 的全部运行环境，或将其纳入 100 人并发性能验收。
- 为外部 URL 所属第三方网站提供网络性能或可用性保障。
- AI 生成题库、学习进度画像、自动学习计划、AI 长期记忆及多 Agent 系统。
- 没有明确需求与压测依据的提前分布式化（例如强制引入微服务集群、Kubernetes、消息队列或 Redis）。

## 6. 交付与验收

### 6.1 文档与工程交付

- 当前系统架构分析（As-Is）、业务调用链及问题清单。
- 目标总体架构（To-Be）、职责边界与关键设计决策记录。
- 数据模型、接口契约、插件 Bridge 协议及版本兼容策略。
- 分阶段实施计划、数据迁移与回滚方案。
- 功能回归、并发一致性、安全隔离、静态资源及 AI 基本功能测试。
- 100 人混合负载测试报告，以及真实浏览器体验评估。

### 6.2 验收场景

1. **100 人练习混合负载：** 包括打开题库、切题、保存、提交、重做、历史查看，核对吞吐量、P95/P99 和错误率。
2. **资源并发：** 100 名活跃用户对平台托管的音频、图片等混合资源发起请求，核对网络吞吐、失败率、缓存与分段读取行为。
3. **并发一致性：** 同一用户重复提交或多标签页并发保存，验证不会出现静默覆盖或重复副作用。
4. **跨用户隔离：** 验证任何用户不能读取或修改其他用户的私有练习数据。
5. **异常恢复：** 模拟进程退出、请求超时等情况，核对已确认保存的数据与恢复后的状态。
6. **题型拓展：** 插件初始化、独立渲染、Bridge 保存/提交、操作结果回传、非法消息防护与版本不兼容提示。
7. **题库版本：** 本地开发版领先在线版时，Hub 能识别并合理处理在线版尚不支持的题型/能力。
8. **AI 辅导：** 验证答题中、已评分、重做及切题场景的上下文准确性，以及模型超时不会阻塞核心练习。
9. **真实浏览器：** 人工验证题库加载、题目切换、插件页面性能、手写与移动端浏览器基本体验。

## 7. 待架构设计阶段确认

以下为**实现与口径待定项**，不妨碍当前需求基线成立：

- 现有 Hub、Web、云端练习模块的实际依赖与迁移边界。
- 是否继续沿用独立 Node.js 练习服务及其与 Java 服务的职责分配。
- MySQL、文件/对象存储等数据所有权与事务边界；现有数据迁移策略。
- 题目作答状态机、重做次数定义、保存幂等性与并发冲突策略。
- 题型 Bridge API 的具体字段、能力协商、版本管理和运行隔离规则。
- 平台托管与外部 URL 资源的标识、权限、缓存和错误恢复机制。
- AI 上下文接口、短期对话保留范围和未提交时的答案保护方式。
- 测试服务器规格、数据规模、用户操作频率、静态资源组合与浏览器性能阈值。

## 8. 需求变更管理

本文件为 **v1.0 初始需求基线**，不代表需求永久冻结。

后续发现问题、新需求或更优方案，可以修改需求。每次变更须：

1. 明确变更内容和原因。
2. 评估对架构、数据协议、兼容性、开发排期和测试的影响。
3. 更新需求文档及相关设计/验收方案。
4. 通过 Git 提交记录修改，重大变更采用 Pull Request 评审。

本次重构遵循 **需求基线 → 现状分析 → 总体架构 → 详细设计 → 分阶段实现 → 性能与质量验收 → 部署运维** 的迭代研发流程。
