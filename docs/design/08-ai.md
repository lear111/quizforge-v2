## 1. 余额与流水

### 1.1 表

| 表 | 角色 | 操作 |
| --- | --- | --- |
| `ai_account`（每用户一行） | 当前余额的唯一来源；并发扣费时的锁 | 加锁读、更新 |
| `ai_ledger` | 每一笔余额变动的历史 | **只插入**，不修改、不删除；记错用冲正流水 |

流水字段要点：`user_id`、**`seq`**（该用户的流水序号 1、2、3…，在余额行锁内分配，`ai_account.ledger_seq` 记录最后一笔）、`delta`（正为增加）、**`balance_after`**（这笔之后的余额）、`kind`、`ref`（关联的来源）、`created_at`；管理员调整另记操作人（`actor_id`）与原因（`reason`）。唯一约束 `(kind, ref)`：同一来源只能入账一次（纵深防御）；唯一约束 `(user_id, seq)`。

| `kind` | 含义 | `ref` |
| --- | --- | --- |
| `default_credit` | 默认额度 1 元（需求 FR-09 v1.12）：新用户注册时、V16 为已有用户补发、迁移老用户时 | 用户 ID（因此每个用户只能得到一次，不论经由哪条路径） |
| `redeem` | 兑换码充值 | 兑换码记录 ID |
| `ai_call` | AI 调用扣费（L5.2） | AI 任务 ID 或请求 ID |
| `admin` | 管理员增减 | 本次调整的 ID（UUIDv7） |
| `migration` | 保留未用（旧余额不迁移，见第 0 节） | — |
| `refund` | 退款或冲正（预留） | 被冲正的来源 |

金额单位为 0.0001 元（10000 = 1 元），全部为 `BIGINT`。兑换码表 `ai_redeem_code` 见 1.3。

### 1.2 规则

1. **每次 AI 调用都写一条流水**（旧平台按天汇总，V2 逐笔记录）。数据量估算：每天 1 万次约每年 365 万行、几百 MB，按 `(user_id, created_at)` 建索引；以后可归档。
2. **所有余额变动走同一个函数**：锁住余额行（`SELECT … FOR UPDATE`）→ 计算 → 更新余额 → 插入流水，在同一事务内。任何地方都不得直接 `UPDATE ai_account`。
3. 使用**悲观锁**而不是乐观锁：扣费冲突不需要用户决定，等前一笔完成后用最新余额重算即可；锁只影响同一用户。
4. **余额可以为负**：发起请求前普通读检查余额 > 0，否则提示充值；请求结束后按实际用量如实扣费。充值先抵扣欠款（加法自然成立）。界面显示负数（欠费）。
5. 透支上限 ≈ 每用户并发数（2）× 单次请求最高费用（由 `max_tokens` 上限决定）。
6. 对账任务定期检查 `余额 = Σdelta` 及流水 `balance_after` 的连续性（第一笔 `seq = 1` 且 `balance_after = delta`，之后 `seq` 连续、`balance_after = 上一笔 + delta`），不一致时记录告警日志。默认每小时一次（`QF_AI_RECONCILE_INTERVAL_MS`），也可手动执行 `java -jar app.jar maintenance ai-reconcile`（一致返回 0，不一致输出明细并返回 3）。
7. 余额行在注册时与账号同一事务创建（V16 为已有用户补建），加锁读的永远是已存在的行，不产生间隙锁；缺少余额行时变动入口抛出 `IllegalStateException`，读取按 0 显示。

### 1.3 兑换码

沿用旧平台规则：格式 `AI-XXXX-XXXX-XXXX-XXXX`（16 位，字母表去掉 I、L、O、U）；输入忽略大小写、空白与连字符，O→0、I/L→1。

- 库中只存规范化码体的 SHA-256 与前缀（`AI-XXXX`），完整码用 AES-256-GCM 加密保存（附加数据 `quizforge-redeem-code-v1`，格式 Base64(IV ‖ 密文 ‖ 标签)）。密钥来自环境变量 `QF_AI_MASTER_KEY`（32 字节的 Base64）；`provider` 模式或站点来源不是本机 / `.test` 时缺少密钥启动失败，只有本机 `fake` 模式使用固定的开发密钥。
- 管理员批量生成（1–200 个，面额 0.01–10000 元，有效期 1–3650 天，备注 ≤ 60 字）；完整码只在生成的响应中返回一次，页面可导出为文本文件；列表只显示前缀；未兑换的码可停用，已兑换的不能停用。生成、停用都写 `admin_audit`。
- 兑换：同一事务内条件更新 `redeemed_at IS NULL AND revoked_at IS NULL AND expires_at > now`（并发兑换同一个码只有一个影响 1 行）→ 写 `redeem` 流水。无效、已使用、已停用、已过期统一提示；同一用户 1 小时内失败 10 次锁定 1 小时（单实例内存计数，与旧平台一致）。
- 网页兑换接口 `POST /api/account/ai/redeem`；客户端的 `/api/connect/redeem` 属于 L6。

### 1.4 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/account/ai` | 会话用户的余额 `{balance, overdrawn}` |
| `GET /api/account/ai/ledger?before=&limit=` | 会话用户的流水，按 `seq` 倒序键集分页（`nextBefore`），不含操作的管理员 |
| `POST /api/account/ai/redeem` | 兑换 `{code}` → `{added, balance}` |
| `GET /api/admin/users/{id}/ai` | 管理员：余额与最近 20 条流水 |
| `POST /api/admin/users/{id}/ai-balance` | 管理员增减 `{delta, reason}`，原因必填（≤ 200 字），单次 ≤ ±100 万元 |
| `GET/POST /api/admin/ai-codes`、`POST /api/admin/ai-codes/{id}/revoke` | 兑换码列表、生成、停用 |

**给 L5.2 的服务方法**（`AiBalanceService`）：

- `hasPositiveBalance(userId)`：发起调用前的普通读检查（不加锁），为 `false` 时提示充值，不发起调用。
- `charge(userId, amount, ref)`：调用结束后按实际费用扣费，`amount > 0`，写 `ai_call` 流水，`ref` 为 AI 任务 ID 或请求 ID（≤ 100 字符）；可以扣成负数。同一 `ref` 重复扣费抛出 409（`LEDGER_DUPLICATE`）且余额不变，因此重试时可以安全地再调用一次。必须在模型调用（慢操作）**之后**、单独的短事务中调用，不要把模型调用包进事务。
- 其他来源的变动统一调用 `change(userId, delta, kind, ref, actorId, reason)`，不直接写表。

### 1.5 模型接入（L5.2）

- **客户端：** LangChain4j 1.22.0 的底层 API（`langchain4j-open-ai`：`OpenAiChatModel` / `OpenAiStreamingChatModel`、`ChatRequest`、`ChatResponse`），不使用 starter、AI Services 或 ChatMemory。全站一个兼容 OpenAI 的上游，地址与模型 ID 由环境变量 `QF_AI_BASE_URL`、`QF_AI_MODEL` 提供（只接受 HTTPS），调用方传入的模型名一律被替换。
- **统一入口 `AiGateway`：** `chat(userId, ChatRequest, ref)` 同步；`stream(userId, ChatRequest, ref, handler)` 流式。请求可带工具定义，回复保留工具调用请求，工具循环由调用方实现，每次模型调用单独计费、ref 各不相同。图片只接受 PNG / JPEG / WebP 的 base64 或 data URL，单张 ≤ 4 MiB、合计 ≤ 12 MiB。`max_tokens` 不得超过 `QF_AI_MAX_OUTPUT_TOKENS`（默认 8192），未给出时取上限。
- **流程：** ① 普通读检查余额 > 0，否则 402「余额不足，请充值」；② 每用户并发 2、全站并发 `QF_AI_SITE_CONCURRENCY`，超出立即 429（单实例内存实现，`AiConcurrencyLimiter` 可换 Redis）；③ 按顺序最多尝试 3 个 Key；④ 成功后费用 = ceil((输入 token × 输入单价 + 输出 token × 输出单价) / 1,000,000)，至少 1 个单位，单价取所用 Key 的配置，调用 `charge`，409 按已扣处理；⑤ 超时、网络错误、5xx、流式中途出错等没有得到完整回复的调用不扣费。
- **Key 池（`ai_upstream_key`，V19）：** 最多 20 个；启用 / 停用、到期时间、输入与输出单价（0.0001 元 / 百万 token）、备注；Key 用 `QF_AI_MASTER_KEY` 做 AES-256-GCM 加密保存（附加数据 `quizforge-upstream-key-v1`），只写不读，后台只显示末 4 位。401 / 403 / 402 与欠费类错误码把 Key 标为不可用并告警（启用或测试通过后恢复）；429、5xx、超时、网络错误换下一个 Key；400 / 404 等请求本身的问题直接失败。
- **超时与租约：** 单次上游调用超时 `QF_AI_CALL_TIMEOUT`（默认 40 秒；流式为等到首个片段的时间）。同步调用最长 ≈ 超时 × 3 个 Key；启动时检查 `超时 × 3 + 10 秒 < AI 任务租约（150 秒）`，否则启动失败。流式回复整体上限 `QF_AI_STREAM_TIMEOUT`（默认 300 秒），只用于交互式的辅导，不受租约约束。
- **流式计费：** 请求固定带 `stream_options.include_usage = true`，用量在最后一个事件。客户端断开（handler 的 onPartial 抛出异常）后网关不再转发片段，但继续读完上游、按用量扣费；名额在读完上游后才归还，因此透支上限仍是“每用户并发 × 单次最高费用”。上游返回成功却没有用量时按最低 1 个单位扣费并记录告警（与旧平台一致）。
- **日志：** 每次调用一行：用户 ID、ref、Key 的 ID、输入 / 输出 token、费用、耗时、结果；不记录 Key、请求正文与图片（LangChain4j 的请求与响应日志关闭）。

## 2. AI 任务（异步判分）

### 2.1 两层幂等

| 编号 | 生成者 | 防止 |
| --- | --- | --- |
| `requestId` | 浏览器，每次用户操作一个，重试不变 | 浏览器重发导致重复**创建**任务（沿用回执表） |
| `taskId` | 服务器，创建任务时生成 | 重复**处理**同一个任务 |

用户主动再次点击“AI 评分”是新操作、新任务，正常扣费（FR-14 可反复评分）。

### 2.2 状态与检查点

`pending` → `running` → `model_returned` → `succeeded`；以及 `failed`。

```text
取出任务
 ① 查状态：succeeded → 跳过；model_returned → 跳到 ③；pending/running → ②
 ② 事务外调用模型；返回后立即用短事务保存模型输出与 token 用量，状态 model_returned
 ③ 一个事务：锁余额行 → 按已保存的用量扣费并插入流水（ref = taskId）→ 写判分结果 → 状态 succeeded
```

| 崩溃时机 | 用户被扣 | 平台付模型费 |
| --- | --- | --- |
| ② 模型未返回 | 1 次 | 1～2 次 |
| ② 保存后、③ 之前 | 1 次（从检查点继续） | 1 次 |
| ③ 之后 | 1 次（跳过） | 1 次 |

模型已返回但尚未保存时崩溃的窗口只有几毫秒，平台多付一次模型费，用户仍只扣一次（流水唯一约束），可以接受。

### 2.3 队列：先用数据库，不引入 RabbitMQ

- **判断依据：** 量最大的 AI 辅导是同步流式调用，不经过队列；需要排队的只有异步判分。判分的瓶颈是上游模型（并发、限流、费用），不是队列吞吐：极端场景 300 人 × 20 道主观题 = 6000 个任务，入队几秒钟，处理受模型并发限制需要约一小时，换成 RabbitMQ 也不会更快。
- **做法：** 任务表即队列。创建任务与业务数据在同一事务中，**不存在双写问题，不需要 Outbox**。多个消费者用 `SELECT … FOR UPDATE SKIP LOCKED` 取任务；`ORDER BY priority, created_at` 实现优先级（用户在等的手动评分优先，考试批量判分靠后）；`next_attempt_at` 实现退避重试；超过重试次数置为 `failed`。
- **以后何时换：** 任务量持续每秒几百个以上，或有多个不同服务需要订阅同一类事件。代码中保留 `AiTaskQueue` 接口，届时以 Outbox + RabbitMQ 实现替换。
- **全局并发：** 部署多实例后，全站同时调用模型的数量用 Redis 计数控制。

### 2.4 租约、重试与用户体验

- **用户可以一直等**：AI 评分不阻塞用户，界面不设超时，显示“AI 评分中”，期间可以继续做题或随时人工打分。
- **人工打分中断 AI 评分**：`grading_generation + 1`；尚未开始的任务直接取消，正在调用模型的任务结果返回后丢弃（照常扣费，FR-14）。
- **租约**：领取任务时设置 `locked_until = now + 租约时长` 并 `attempts + 1`；领取查询同时选取 `pending` 与 `running 且 locked_until < now` 的任务。租约时长必须大于一次任务内模型调用的最长时间（单次模型超时 × 最多尝试的 Key 数 + 余量，初值 150 秒），以免把“慢但还活着”的消费者误判为崩溃。
- **重试上限**：最多 3 次，间隔递增（退避，`next_attempt_at`）；全部失败后置为 `failed`，界面显示“AI 评分失败，可以重新评分”，题目保持待评分，不扣费。
- **栅栏令牌**：消费者记住自己领取时的 `attempts`，所有写入带 `WHERE attempts = ?`；任务已被他人重新领取时旧消费者写入影响 0 行，结果丢弃。用户仍只扣一次（流水唯一约束）。与 `revision`、`grading_generation` 同一思路：用只增不减的编号识别过时的写入。

## 3. AI 辅导（L5.3，2026-11-03）

### 3.1 范围与模块边界

- 第一版只做**服务器模式**（平台 Key，经 L5.2 的 `AiGateway` 调用与计费）。“用户自己的 Key、浏览器直接调用模型”放到之后（3.8），复用本节的上下文、工具与历史接口。
- 代码位于 ai 模块的 `ai.tutor` 包，表以 `ai_tutor_` 为前缀。**不直接读 practice 的表**：通过 practice 模块提供的“辅导只读视图”接口（3.4）读取题目、作答与提交状态。
- 会话**不绑定题目**：一个会话可以讨论多道题，每条用户消息记录发送时的“当前题目”。

### 3.2 表

| 表 | 字段要点 |
| --- | --- |
| `ai_tutor_session` | id, user_id, title（默认取第一条消息的前 30 字，可改名）, created_at, updated_at, deleted_at；索引 (user_id, deleted_at, updated_at) |
| `ai_tutor_message` | id, session_id, user_id, seq（会话内递增）, role（user / assistant / tool）, content（文本，上限见 3.7）, context_id, question_id（发送时的当前题目，可空）, **reveal_context_id / reveal_question_id / reveal_generation**（该消息含有某题答案时，记录该题当时的提交代次）, tool_name / tool_call_id（role=tool）, input_tokens, output_tokens, cost, ref（计费 ref）, request_id, created_at；唯一 (session_id, seq)、(user_id, request_id) |

### 3.3 一条用户消息的处理流程

```text
POST /api/ai/tutor/sessions/{id}/messages  {requestId, contextId?, questionId?, text}
1. 校验：会话归属；文本长度；requestId 幂等（重复请求返回原结果，不重复调用模型）
2. 保存用户消息（短事务）
3. 组装上下文（3.5）
4. 调用 AiGateway.stream（事务外），附带工具（3.4）；工具循环最多 3 轮，每轮一次模型调用、各自计费，ref = tutor:{消息 ID}:{轮次}
5. 逐段通过 SSE 推送给浏览器；结束后保存工具调用、工具结果与助手回复（短事务），标记 reveal_*（3.6）
```

余额不足、并发超限、请求不合法等错误由 `AiGateway` 抛出，在 SSE 开始前以普通 HTTP 错误返回。

### 3.4 工具与“辅导只读视图”

practice 模块新增只读接口 `TutorQuestionView view(userId, contextId, questionId)`，返回：题目标题、**安全投影**（与读题相同，未提交时不含答案）、我的当前作答、是否已提交、提交代次、评分结果；**只有已提交时**才包含参考答案与解析（原始数据或提交后投影）。归属检查在 SQL 中完成。

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `get_question` | questionId | 安全投影与题目标题 |
| `get_my_answer` | questionId | 我的作答与状态 |
| `get_reference_answer` | questionId | **调用时**检查是否已提交：已提交 → 参考答案与解析；未提交 → “这道题还没有提交，不能提供答案” |
| `list_questions` | — | 当前练习中各题的标题与状态（不含内容），用于“第几题”的定位 |

工具只在用户当前所在的练习上下文（contextId）内查询；模型给出的 questionId 只当作参数，归属与状态都由服务器重新检查。

### 3.5 上下文组装

```text
系统指令：辅导老师的角色；未提交题目不能直接给出答案，引导用户思考；需要答案时调用工具
+ 当前题目：标题、安全投影、我的作答、是否已提交（未提交时没有答案）
+ 最近的历史：最多 20 条消息且不超过约 8000 token（从新到旧截取），排除失效的“含答案消息”（3.6）
+ 本条用户消息
```

题干中的图片转为 data URL 附在当前题目中，单张不超过 4 MiB、合计不超过 12 MiB（与 L5.2 一致），超出时只给文字说明。

### 3.6 上下文版本（防止旧答案泄露）

某条消息含有某题答案（`get_reference_answer` 成功返回，或之后基于它的助手回复）时，记录 reveal_* = 该题当时的 context_id、question_id 与提交代次。组装上下文时，若该题**当前**未提交或提交代次已变化（用户点了“再试一次”），这些消息**不放入上下文**（数据库中仍保留，用户自己可以查看）。

### 3.7 限制

| 项 | 值 |
| --- | --- |
| 用户消息长度 | 4000 字 |
| 单次回复 max_tokens | 不超过 L5.2 的上限 |
| 工具轮数 | 每条用户消息最多 3 轮 |
| 每用户会话数 | 200（超出时提示删除旧会话） |
| 并发 | 由 `AiGateway` 的每用户 2 个控制 |

### 3.8 之后：用户自己的 Key（浏览器直接调用）

用户在设置中填写兼容 OpenAI 的地址、模型与 Key，只保存在浏览器本地。浏览器调用新的接口 `POST .../messages/prepare` 取得服务器组装的上下文与工具定义，自己调用模型；工具调用仍请求服务器执行（`POST .../tools/{name}`）；最后把回复提交服务器保存（`POST .../messages/complete`）。服务器不计费。未提交时拿不到答案的保证不变（上下文与工具都由服务器决定）。

## 4. AI 判分（L5.4）

沿用旧版拓展协议（C-02，`prepareAiGrading` / `review`，见旧 `API.md`），由服务器执行：

1. 用户点“AI 评分”（或开启自动评分时提交后自动触发）：创建 AI 任务（第 2 节的表、两层幂等、检查点、租约、栅栏）。任务绑定提交代次与评分代次。
2. 后台取任务：rule-runner 执行拓展的 `prepareAiGrading`，得到 `{question, answer, referenceAnswer, maxScore, scoreStep}`（图片以 assetId 引用，宿主转为 data URL）；宿主用统一的系统指令要求模型输出 `{score, feedback}` JSON；经 `AiGateway.chat` 调用（ref = grading:{taskId}:{attempts}）。
3. 宿主校验输出格式（分数为有限数、反馈非空且有长度上限）；格式错误最多修复一次（共享 3 次调用上限）。
4. 采用：rule-runner 执行拓展的 `review(data, answer, {score, feedback})` 得到最终结果，按评分代次条件写入，评分来源 ai。人工打分使评分代次 +1，进行中的任务结果丢弃（照常扣费，FR-14）。
5. 小题评分（targets）、自动评分计划沿用旧协议；第一版可先只支持整题，小题在 PR 中说明是否实现。
6. 浏览器判分（ADR-011）不影响 AI 判分：AI 判分始终在服务器执行。

### 4.1 L5.4 落地约定（2026-11-04）

- 作者确认以旧 `API.md` / `ai-protocol.js` 为评分输入输出契约：宿主不限制候选分数范围、精度或步长，由 `review` 决定是否采用。模型反馈上限 18000 字符，合并后的反馈上限 20000 字符；最终分数依既有存储规则 HALF_UP 四位小数。
- 数据库状态使用 `queued / running / model_returned / succeeded / failed / superseded / confirmed`；`model_returned` 对旧页面显示为 `running`。`succeeded` 表示已有有效候选、拓展尚未采用，`confirmed` 表示已经采用。
- 同一目标的活动任务复用，包括 `force`；`requestId` 重放与目标绑定分别负责操作幂等、目标换代。整题与小题绑定互斥，小题之间独立。
- 自动评分登记和提交结果写入同一事务；准备材料、模型调用与 review 都在事务外。复用现有生命周期数据库轮询器和网关执行器，不新建线程池。
- `attempts` 是租约栅栏，`model_calls` 统计真实模型尝试（最多 3 次，含换 Key 与一次格式修复）。检查点保留模型正文、用量、费用、Key ID 与原 ref；恢复后不重新调用模型。
- 模型返回后先落检查点，再在结果采用事务中使用幂等结算；人工评分等使任务失效时，已返回的调用仍按保存的 ref 结算，不采用旧结果。
- 自动 targets 计划先完整校验，再原子登记（最多 256 个唯一目标）；同题兄弟任务只在 revision 竞争时重新 review，保留模型检查点。
- HTTP 请求上限 8 KiB，材料上限 1 MiB；图片经资源权限检查后读取，单张 4 MiB、合计 12 MiB。任务视图不包含材料、原始题目、检查点或图片 data URL。

实现与本机冒烟命令见 [L5.4 AI 评分说明](../notes/l5-ai-grading.md)。
