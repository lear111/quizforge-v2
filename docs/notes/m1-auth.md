
1. 为什么用服务端会话，不用 JWT？（你还没写）

核心是能否立即作废。封禁账号、修改密码、退出登录后，删除数据库里那一行，下一个请求就失效。JWT 签发后在过期前一直有效，要提前作废就得维护黑名单，每个请求都去查，这样又变回了有状态，失去了它最大的优点。我们是单体应用，也不需要在多个服务之间无状态地共享登录。代价是每个请求按主键查一次数据库，很快。

2. 为什么只存哈希，两种算法为什么不同？ 前半部分对。补上 SHA-256 的原因：

算法的选择取决于被保护的东西有多容易猜。令牌是 256 位真随机数，暴力猜测完全不可能，所以用快速的 SHA-256 就够了，而且每个请求都要算一次，必须快。密码是人取的，随机性很低，所以要用故意又慢又耗内存的 scrypt，再加上 salt，让暴力破解的成本极高。

3. 用户不存在为什么也要计算哈希？ 对。把术语也记上：

防止用户枚举。用户不存在和密码错误时，返回相同的状态码、错误码、提示信息，并且耗时也一样（都算一次 scrypt），攻击者没法判断某个邮箱是否注册过。

4. 事务相关： 方向都对，有两处说得更准确会更好。

为什么用事务： 这是 ACID 里的原子性：插入用户和创建会话，要么都成功，要么都回滚。否则会出现"用户已创建、会话却没建好"，用户重试时又提示"邮箱已注册"。
为什么 scrypt 放在事务外： 主要原因不是"故障概率更大"，而是资源占用：事务从开始到结束一直占着一个数据库连接，连接池只有 20 个。在事务里做几十毫秒的 CPU 计算，连接就白白被占着，其他请求可能借不到连接，只能排队。
为什么不能拆成同一个类的另一个方法： 准确的说法是"注解会被悄悄忽略"，而不是"用不了"：@Transactional 靠代理实现，同一个类里用 this 调用不经过代理，注解不生效，也不会报错。这才是它危险的地方。

5. 请求经过 Spring Security 的哪些步骤？ 顺序说对了（先 Origin 校验，再身份认证）。补上后半段：

① OriginCheckFilter：写请求的来源必须是本站，否则 403。② SessionAuthenticationFilter：从 Cookie 取令牌，查会话表，查到就把用户放进 SecurityContext（基于 ThreadLocal）；查不到不报错。③ AuthorizationFilter：根据规则判断这个接口是否需要登录；需要但 SecurityContext 里没有用户，就由 ExceptionTranslationFilter 交给 AuthenticationEntryPoint，返回 401。认证只回答"你是谁"，授权才决定"能不能访问"。

另外，我们目前还没有做"权限"（比如管理员角色），现在只区分"登录"和"没登录"。

6. CSRF： 对，再说清楚"为什么能关掉 CSRF Token"：

我们用两道防线替代 CSRF Token：一是 Cookie 设置 SameSite=Lax，浏览器从别的网站发起 POST 时不会带上我们的 Cookie；二是服务器校验 Origin 头，网页上的 JS 无法伪造它。另外有一条设计规则配合：GET 请求绝不能修改数据。

7. 踩过的坑： assert 那条可以说得更准确，再把其他几个坑也记上，面试问"遇到过什么问题"时很好用：

assert 关键字默认是关闭的，只有 JVM 加 -ea 参数才会执行。Maven 恰好默认开启了，所以测试"看起来"能工作，但很脆弱，失败时的信息也很少。测试要用断言库（AssertJ）。
过滤器写好了却没注册，65 个测试照样全部通过。教训：测试通过不等于功能实现了，要确认有测试真正覆盖到这段代码。
@Value 漏写，Spring 去容器里找一个 String 类型的 Bean，报 NoSuchBeanDefinitionException。学会从最后一个 Caused by 读出是哪个 Bean、第几个参数出了问题。
Optional 和 null 比较：Optional 永远不是 null，要用 isEmpty()。
过滤器不能加 @Component，否则 Spring Boot 会把它额外注册到 Servlet 过滤器链，每个请求执行两次。
