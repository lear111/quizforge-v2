# M1 认证模块工程笔记

> **作者：** 王国松
> **日期：** 2026-10-28
> **范围：** M1 账号与会话（PR #17、#18、#19、#21、#22）
> **相关决策：** [ADR-005 服务端会话认证](../adr/ADR-005-session-auth.md)

本笔记记录 M1 中关键设计的理由和踩过的坑，供复盘和面试准备使用。

## 1. 为什么用服务端会话，不用 JWT？

核心是**能否立即作废**。封禁账号、修改密码、退出登录后，删除数据库里那一行，下一个请求就失效。JWT 签发后在过期前一直有效，要提前作废就得维护黑名单，每个请求都去查，这样又变回了有状态，失去了它最大的优点。我们是单体应用，也不需要在多个服务之间无状态地共享登录。代价是每个请求按主键查一次数据库，很快。

## 2. 为什么只存哈希？两种算法为什么不同？

只存哈希是为了**防止数据库泄露后被直接利用**：拿到哈希无法还原出令牌或密码。

算法的选择取决于**被保护的东西有多容易猜**：

- **会话令牌**是 256 位真随机数，暴力猜测完全不可能，所以用快速的 SHA-256 就够了；而且每个请求都要算一次，必须快。
- **密码**是人取的，随机性很低，所以要用**故意又慢又耗内存**的 scrypt，再加上 salt，让暴力破解的成本极高。

## 3. 用户不存在时为什么也要计算哈希？

防止**用户枚举**。用户不存在和密码错误时，返回**相同的状态码、错误码、提示信息**，并且耗时也一样（都算一次 scrypt，用户不存在时用一个假哈希），攻击者无法判断某个邮箱是否注册过。

## 4. 注册流程中的事务

- **为什么用事务：** ACID 里的**原子性**。插入用户和创建会话，要么都成功，要么都回滚。否则会出现“用户已创建、会话却没建好”，用户重试时又提示“邮箱已注册”。
- **为什么 scrypt 放在事务外：** 主要是**资源占用**。事务从开始到结束一直占着一个数据库连接，连接池只有 20 个。在事务里做几十毫秒的 CPU 计算，连接就白白被占着，其他请求可能借不到连接，只能排队。
- **为什么用 `TransactionTemplate`，而不是拆到同一个类的另一个 `@Transactional` 方法：** `@Transactional` 靠代理实现，同一个类里用 `this` 调用不经过代理，**注解会被悄悄忽略，也不会报错**。这才是它危险的地方。

## 5. 一个请求经过 Spring Security 的步骤

1. **`OriginCheckFilter`**：写请求（非 GET/HEAD/OPTIONS）的 `Origin` 必须是本站，否则 403 `ORIGIN_REJECTED`。
2. **`SessionAuthenticationFilter`**：从 Cookie `__Host-qf_session` 取令牌，哈希后查会话表；查到就把用户放进 `SecurityContext`（基于 `ThreadLocal`）。**查不到不报错**，只是不设置用户。
3. **`AuthorizationFilter`**：根据规则判断这个接口是否需要登录。需要但 `SecurityContext` 里没有用户，就由 `ExceptionTranslationFilter` 交给 `AuthenticationEntryPoint`，返回 401 `UNAUTHENTICATED`。

认证只回答“你是谁”，授权才决定“能不能访问”。目前还没有角色权限（如管理员），只区分“已登录”和“未登录”。

## 6. CSRF 防护

CSRF（跨站请求伪造）：恶意网站诱导浏览器带着用户的 Cookie 向我们发请求。我们用两道防线替代 CSRF Token：

- Cookie 设置 `SameSite=Lax`，浏览器从别的网站发起 POST 时不会带上我们的 Cookie；
- 服务器校验 `Origin` 头，网页上的 JS 无法伪造它。

另有一条设计规则配合：**GET 请求绝不能修改数据**（`Lax` 允许跨站 GET 导航携带 Cookie）。

## 7. 踩过的坑

- **测试里用了 `assert` 关键字**：它默认是关闭的，只有 JVM 加 `-ea` 参数才会执行。Maven Surefire 恰好默认开启，所以测试“看起来”能工作，但很脆弱，失败时的信息也很少。测试要用断言库（AssertJ）。
- **过滤器写好了却没注册**，65 个测试照样全部通过。教训：**测试通过不等于功能实现了**，要确认有测试真正覆盖到这段代码。
- **`@Value` 漏写**：Spring 去容器里找一个 `String` 类型的 Bean，启动报 `NoSuchBeanDefinitionException`。学会从最后一个 `Caused by` 读出是哪个 Bean、第几个参数出了问题。
- **`Optional` 和 `null` 比较**：`Optional` 永远不是 `null`，`user == null` 恒为假，会导致用户不存在时抛 500，还泄露了用户是否存在。要用 `isEmpty()`。
- **过滤器不能加 `@Component`**：否则 Spring Boot 会把它额外注册到 Servlet 过滤器链，每个请求执行两次。
