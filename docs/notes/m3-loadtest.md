# M3 压测与性能调优笔记

> **作者：** 王国松（与 Claude 共同整理）
> **日期：** 2026-10-31
> **范围：** 练习核心（读题、保存草稿、提交判分）的本地负载测试与瓶颈分析，PR #62～#65 及后续优化
> **相关：** [需求 FR-04](../requirements/01-requirements.md)、[rule-runner 协议](../design/03-rule-runner-protocol.md)、[loadtest/README.md](../../loadtest/README.md)

本笔记记录一次完整的性能调优过程：**压测 → 观察指标 → 提出假设 → 加测量验证 → 只改一个变量 → 再压测对比**。每个结论都附有当轮的数据。

## 0. 环境与方法

### 0.1 被测环境

本机 Docker Desktop（WSL2），用容器配额模拟正式服的 4 核 8G：

| 服务 | CPU 配额 | 内存上限 |
| --- | --- | --- |
| app（Spring Boot） | 1.5 核 | 3 GiB（堆 2 GB） |
| mysql | 1 核 | 3 GiB |
| rule-runner | 1.25 核 | 1.5 GiB |
| nginx | 0.25 核 | 0.5 GiB |

监控（Prometheus、Grafana）和压测工具（k6）在这 4 核 8G 之外，避免和被测系统抢资源。

### 0.2 场景（负载测试 Load Testing）

- 100 个虚拟用户（VU），每个 VU 对应一个独立账号
- **逐步加压**（ramp-up）：1 分钟从 0 增加到 100 人 → 保持 3 分钟 → 30 秒逐步减少
- 每轮迭代模拟一个真实用户：打开题库（overview）→ 读题 → 思考 3～8 秒 → 保存草稿 2 次 → 提交 → 看结果
- 加入**思考时间**（think time）：真实用户大部分时间在读题和思考，不是一直发请求
- 已提交的题只读不写（否则会产生大量正常的 409，污染错误率）

阈值（第一版，偏宽松，后续按基线调整）：catalog / draft P95 < 1s，overview < 5s，read < 500ms，submit < 2s，错误率 < 1%。

### 0.3 观测手段

| 层 | 工具 | 关注 |
| --- | --- | --- |
| 客户端 | k6 汇总 | 每类请求的 P95 / P99、最大值、错误率 |
| 应用 | Micrometer → Prometheus | HTTP 直方图（按路由模板）、HikariCP 连接池、rule-runner 调用耗时、舱壁占用与拒绝、Caffeine 命中率、GC、CPU |
| rule-runner | 自带 Prometheus 端点 | **排队时间**与**执行时间**分开统计、工作进程启动/停止次数（按原因） |
| 容器 | Docker Engine stats | 各容器 CPU 用量、**CFS 限流周期比例** |
| 代码 | JFR + 火焰图 | CPU 热点、内存分配热点 |

分析方法：**USE**（资源的使用率 Utilization、饱和度 Saturation、错误 Errors）和 **RED**（服务的请求速率 Rate、错误 Errors、耗时 Duration）。

### 0.4 为什么看 P95 而不是平均值

100 个请求中 99 个 10ms、1 个 5s，平均值是 60ms，看起来很快，但那 1 个用户等了 5 秒。**百分位数反映的是用户的真实体验，平均值会掩盖长尾。** 中位数和 P95 差距很大时，通常意味着有请求在排队。

## 1. 第一轮：所有阈值通过，但提交有长尾

配置：rule-runner 工作进程上限 4（每个拓展最多 2 个），Java 端舱壁 8。

| 请求 | 中位数 | P95 | 最大 |
| --- | --- | --- | --- |
| catalog | 4.9ms | 9.7ms | 14ms |
| overview | 4.1ms | 18ms | 91ms |
| read | 4.9ms | 34ms | 1.55s |
| draft | 16ms | 36ms | 100ms |
| **submit** | **76ms** | **972ms** | 1.69s |

- 吞吐 25 请求/秒，失败 8 次（0.11%）
- **提交的 P95 是中位数的 13 倍**：判分本身不慢，慢的请求大多在等待

查 Prometheus：

| 指标 | 结果 | 结论 |
| --- | --- | --- |
| 失败的状态码 | 全部是 503 | 不是冲突（409），也不是规则超时（422） |
| 舱壁拒绝次数 | 约 7 次 | 失败全部来自 rule-runner 舱壁拒绝 |
| rule-runner 超时 | 0 | 650ms 超时没有误伤 |
| Java 端 rule-runner 调用 P95 | submit 0.91s，project 0.70s | rule-runner 这一侧本身就慢 |
| 连接池等待（pending） | 0 | **数据库不是瓶颈** |

结论：**瓶颈在 rule-runner。**

## 2. 插曲：压测脚本本身也需要验证

第一轮 `iteration_duration` 的中位数正好是 5.0 秒，等于"打开题库 2 秒 + 读题 3 秒"，也就是"题目已提交，直接跳过"的路径。原因：每个用户有 6 本题库，随机选一本时 5/6 的概率选中只有 1 道题的基础题库，提交一次后就只能跳过。2188 次迭代中只有 845 次真正提交，**实际写入压力只有设计的一半左右**。

修复：80% 概率选择 300 道题的压测题库。修复后提交次数从 845 增加到 1152（+36%），迭代中位数变为 18.7 秒，大部分迭代走完了完整的作答流程。

> 经验：**压测脚本模拟出的行为要先核对**，否则得出的结论建立在错误的负载上。

## 3. 定位 rule-runner 的进程抖动

### 3.1 先加测量

Java 端只能看到"调用 rule-runner 一共花了多久"，分不清时间花在排队、启动进程还是执行代码上。于是给 rule-runner 增加了分阶段指标（PR #64）：排队时间、执行时间（含冷启动）、工作进程启动次数、按原因统计的停止次数。**只加测量，不改行为。**

### 3.2 第二轮数据（进程上限仍为 4）

| 指标 | 数值 |
| --- | --- |
| runner 内**排队**时间 P95 | project 4ms，submit 3ms |
| runner 内**执行**时间 P95 | submit 230ms，**project 410ms** |
| 工作进程启动 | **69 次**（4 分半钟内） |
| 因 LRU 被停止 | **65 次** |
| 503 | 9 次 |

**几乎不排队，但执行很慢；而且几乎每次启动进程都伴随着停掉另一个进程。**

### 3.3 原因：抖动（thrashing）

rule-runner 为每种拓展维护独立的工作进程（隔离不同拓展的代码），总数上限 4。压测涉及的拓展种类多于 4，进程池满了以后，新拓展的请求只能停掉最久未用的进程、再启动一个新的。**启动 Node 进程、建立 VM、加载拓展代码需要几十到几百毫秒**，这些时间算进了"执行"里。

project 的执行时间比 submit 更长：300 道题第一次被读到时投影缓存都是空的，大量 project 正好撞上冷启动。

连锁反应：runner 变慢 → Java 端 8 个舱壁名额被长时间占用 → 后到的请求被立即拒绝 → 503。

### 3.4 提交 = 两次 rule-runner 调用

拆开第二轮提交的 P95（约 640ms）：保存答案（很快）+ 准备投影（缓存未命中时调用 project，P95 410ms）+ 判分（submit，P95 230ms）+ 事务（很快）。410 + 230 ≈ 640，正好对上。**冷缓存时一次提交要调用 rule-runner 两次。**

### 3.5 只改一个变量：进程上限 4 → 8

| 指标 | 第二轮（4） | 第三轮（8） |
| --- | --- | --- |
| 工作进程启动 | 69 | **9**（每种拓展的首次冷启动） |
| LRU 停止 | 65 | **0** |
| runner 执行 P95：submit | 230ms | **97ms** |
| runner 执行 P95：project | 410ms | **199ms** |
| HTTP submit P95 | 639ms | **498ms** |
| 503 | 9 | **1** |

抖动消失，runner 执行时间下降一半以上，503 下降 89%。剩下的 9 次停止原因都是 `idle`（空闲 60 秒正常回收）。

## 4. 瓶颈转移到 app 的 CPU

第三轮中依赖 rule-runner 的提交变快了，**不依赖 rule-runner 的请求却变慢了**：

| 请求 | 第二轮 P95 | 第三轮 P95 | 第三轮最大 |
| --- | --- | --- | --- |
| draft | 122ms | **273ms** | 4.16s |
| overview | 69ms | **144ms** | 3.5s |
| read | 55ms | **124ms** | 3.01s |

保存草稿只写一行和一条回执，根本不调用 rule-runner，却出现了 4 秒的请求。**多种不相关的请求在同一时段一起变慢，说明整个进程卡住了，而不是某个功能慢。** 排查：

| 嫌疑 | 数据 | 结论 |
| --- | --- | --- |
| GC 停顿 | 最长 0.126s | 排除 |
| 数据库连接 | pending 一直为 0 | 排除 |
| app CPU | `process_cpu_usage` 最高 **1.0**（JVM 认为有 2 核，即约 2 核用满，超过 1.5 核配额） | **嫌疑最大** |
| 容器 CFS 限流（性能分析时测得） | app 平均使用 1.47 核，**94.9%** 的调度周期被限流 | **证实** |

原因：之前 rule-runner 慢时，提交请求大量时间在等待，app 的 CPU 反而空闲；runner 变快后，请求更快地回到 app 处理，app 的 CPU 被打满，在 CFS 配额下被周期性强制暂停，所有正在处理的请求一起卡住。

> 经验：**解决一个瓶颈后，下一个瓶颈会暴露出来**（瓶颈转移）。

### 4.1 100 个用户其实只有两三个并发请求

吞吐约 22 请求/秒，平均耗时约 0.1 秒。按**利特尔法则**（Little's Law）：同时在处理的请求数 = 吞吐 × 平均耗时 ≈ 22 × 0.1 ≈ 2～3。**一个 1.5 核的 Spring Boot 应用处理每秒 22 个简单请求就把 CPU 用满，效率明显偏低**，说明某段代码消耗了远超预期的 CPU。这需要性能分析工具来定位，而不是猜。

## 5. 火焰图定位：每次保存都在重建整本题库的快照

### 5.1 性能分析结果

用 JFR 录制压测期间的 CPU 执行采样和内存分配采样，转换成火焰图（PR #65）：

| 发现 | 数据 |
| --- | --- |
| CPU 叶方法最热 | `StringLatin1.replace`，163 / 1301 样本（12.5%） |
| 这些样本的调用者 | **112 个在 `PracticeReadService.collectionSnapshot` 下**，48 个在 overview 下 |
| 内存分配（采样估算） | 67 秒约 23 GB，平均每秒约 350 MB |
| `collectionSnapshot` 占分配的比例 | **53.8%**（含子调用） |

（该次录制是 20 VU 的短测，同机还有其他项目在运行，只用于定位热点，不用于跨轮比较。）

### 5.2 原因

`collectionSnapshot` 生成**整本题库的目录快照**（标题、题序、大纲、每题内容版本），用于创建轮次时冻结题库的样子，**只有每轮第一次提交（创建轮次）时才需要**。但它被放在了 `prepareDraft` 里，而 `prepareDraft` 被两处调用：

```
DraftActionService（每次保存草稿） → prepareDraft → collectionSnapshot   ← 完全用不到
SubmitService（每次提交）          → prepareDraft → collectionSnapshot   ← 一轮中只有第一次用得到
```

每保存一次草稿，都要查出整本题库的全部题目，逐题解析大纲 JSON、转十六进制、组装对象，再序列化成一个大 JSON，然后丢掉。在 300 道题的题库里，一次单题保存的开销被放大了数百倍。

**单次看起来不大**（快照只有约 100 多 KB），但生成过程中产生大量临时对象，再乘以每秒约 10 次的保存和提交，就成了每秒近 200 MB 的内存分配和对应的 GC、CPU 开销。**人的直觉擅长判断单次操作的成本，不擅长判断乘上频率后的成本。**

### 5.3 这个问题是怎么产生的

- 切片 4 时 `prepareDraft` 只为保存草稿准备单题数据，很轻
- 切片 5 时为了让提交在**事务开始前**就拿到快照（缩短持有 context 锁的时间），把快照计算加进了这个**共用**方法
- 保存草稿也调用这个方法，于是被迫多做了这件事
- 功能测试发现不了（结果正确，只是慢）；第一轮压测也发现不了（当时主要是 1 道题的小题库，快照很小）

**为了优化一个低频场景（每轮一次的建轮次），拖慢了一个高频场景（每次作答都会触发的保存）。**

### 5.4 修复：延迟计算

- `prepareDraft` 不再计算快照，恢复为只处理单题
- 新增单独的快照方法，`SubmitService` 只在 `if (roundId == null)`（创建轮次）分支内调用
- 代价：快照改为在事务内、持有 context 锁时计算，持锁时间略增；但每轮只发生一次，且锁只影响该用户的这本题库，可以接受

## 6. 结果对比

| 轮次 | 改动 | submit P95 | draft P95 | read P95 | overview P95 | 失败 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 基线（进程上限 4） | 972ms | 36ms | 34ms | 18ms | 0.11% | 脚本偏向小题库，写入压力偏低 |
| 2 | 脚本改为偏向 300 题题库 | 639ms | 122ms | 55ms | 69ms | 0.13% | 抖动：69 次启动 / 65 次 LRU |
| 3 | 进程上限 4 → 8 | 498ms | 273ms | 124ms | 144ms | 0.01% | 抖动消除；app CPU 打满被限流 |
| 4 | 快照延迟计算 | 待测 | 待测 | 待测 | 待测 | 待测 | 预期 app CPU 下降、draft 明显变快 |

注意：同一配置多次运行的 P95 也可能有 20%～30% 的波动；严格比较时每种配置应运行 2～3 次。

## 7. 经验

1. **先测量，再优化**（Measure, don't guess）。每一步都先加观测、拿数据验证假设，再动手改。
2. **控制变量**：一次只改一处，否则无法判断效果来自哪个改动。
3. **百分位数而不是平均值**；中位数与 P95 差距大，往往意味着排队。
4. **区分排队时间和执行时间**：两者需要完全不同的优化手段（加并发 vs. 减少单次成本）。
5. **压测数据和脚本要接近真实**：只用小题库，快照问题会一直藏着；脚本行为也要先核对。
6. **瓶颈会转移**：修好一处，下一处就会暴露。
7. **修改共用方法前，先查看所有调用方**，尤其是在给它增加开销时；能延迟计算的就不要提前计算。
8. **用户数 ≠ 并发请求数**：用利特尔法则从吞吐和耗时推算真实并发。
9. **容器 CPU 配额会造成"整个进程卡住"的长尾**：CFS 限流时所有请求一起暂停，表现为不相关的接口同时出现秒级慢请求。
