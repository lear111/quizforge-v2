本笔记随 M2 的各步骤逐步补充。目前完成 M2.2（安全解压 `QbankArchiveReader`，PR #30）。上限数值按题库包格式 4（[详细设计 06](../design/06-qbank-package.md)）：单文件 32 MiB、总量 256 MiB、10000 个条目、深度 32。

## 0. 总览：这一层防什么、不防什么

`QbankArchiveReader` 只回答一个问题：**这个 ZIP 能不能被安全地读出来？** 它不理解任何业务含义。

| 类别 | 问题 | 防护 | 结果 |
| --- | --- | --- | --- |
| 资源耗尽 | 解压炸弹 | 边读边计数，单文件超过上限立即中断 | LIMIT |
| | 很多个不超限的文件累计很大 | 累计总量上限 | LIMIT |
| | 几十万个空文件 | 条目数上限 | LIMIT |
| | 头里声明很小，以此骗过检查 | 只相信实际读到的字节数 | LIMIT |
| 路径攻击 | Zip Slip（`../../x`） | 逐段拒绝 `.`、`..` | INVALID |
| | 绝对路径、`a//b` | 拒绝空段 | INVALID |
| | “看起来是空的”文件夹名 | 按 JavaScript 空白字符集合判断空段（含 `U+00A0`、`U+FEFF` 等） | INVALID |
| | 不该有的顶层文件 | 顶层白名单 | INVALID |
| | 深层嵌套 | 深度上限 | INVALID |
| 跨平台 | Windows 上无法创建的文件名 | 禁用字符、结尾空格或点、保留名，逐段检查 | INVALID |
| | 大小写不同的同名文件互相覆盖 | 大小写不敏感查重（`Locale.ROOT`） | INVALID |
| 完整性 | 文件损坏 | 自己计算 CRC32 比对 | INVALID |
| | 记录与内容不符 | 实际大小必须等于声明大小 | INVALID |
| | 本地头与中央目录不一致 | 用 `ZipFile` 只读中央目录 | — |
| | 不是 ZIP、截断、非法 UTF-8 文件名、加密条目 | JDK 的 `IOException` 统一转换 | INVALID |

**不由这一层负责：** 上传大小（上传接口）；空包、格式标识、目录结构、资源类型、`bank.json`（包结构解析）；恶意拓展代码（审核白名单 + rule-runner 隔离）。

**已知差异：** 旧版会拒绝符号链接、设备文件等特殊条目，V2 不拒绝。JDK 的 `ZipFile` 不提供读取 UNIX 文件类型的接口；V2 服务器从不把包内文件写到磁盘，符号链接条目只是一段普通字节；真正解压到磁盘的 Windows / 本地版在导入时自己拒绝特殊条目。如果以后服务器需要落盘，可改用 Apache Commons Compress 读取这些属性。复现测试保留在 `QbankArchiveReaderTest` 中并标记为禁用。

**三条原则：** 不信任输入里的任何声明；在资源耗尽之前中断；只拒绝，不修正。

## 1. 解压炸弹：为什么不能相信 ZIP 头里声明的大小？

**解压炸弹**是一个很小的压缩包，解压后却非常大。例如几百 KB 的 ZIP，里面是一个 10 GB 的全零文件：重复数据的压缩率极高。服务器一旦把它完整解压，内存或磁盘就会被撑爆，所有用户都无法使用。

ZIP 头里确实记录了每个文件解压后的大小，但这个值是**打包的人自己填的**，攻击者可以写“1 KB”，实际数据却是 10 GB。所以：

- **只相信实际读到的字节数。** 头里的大小只用来提前拒绝明显超限的文件（省得白读），不能作为唯一依据。
- **边读边检查，而不是读完再检查。** 每读 8 KB 就累加并比较上限，超过立即中断。读完再检查的话，数据已经进了内存，检查之前服务器就已经被撑爆了。这是“在资源耗尽之前中断”，而不是事后发现。
- 除了单文件上限（8 MiB），还要有**总量上限**（128 MiB）和**条目数上限**（10000），防止“很多个不超限的文件加起来”和“几十万个空文件”。

## 2. Zip Slip：为什么不写磁盘也要校验路径？

**Zip Slip**：把压缩包里的文件名写成 `../../etc/passwd` 这样的路径，解压程序如果直接把文件名拼到目标目录后面，文件就会被写到目录外面，覆盖系统文件或程序代码。

防御方法：路径按 `/` 拆分后**逐段**检查，拒绝空段、`.` 和 `..`。空段同时拦住了绝对路径（`/etc/passwd` 拆分后第一段为空）和 `a//b`。

我们的 `QbankArchiveReader` 不写磁盘，只把“路径 → 内容”交给调用方，但仍然要校验，因为这些路径之后还会被使用：

- 作为题库路径（`bank_key`）和资源路径存进数据库；
- 导出题库、Windows 客户端下载题库时会被**重新打包**，在别人的电脑上解压。

所以不合法的路径从一开始就不能放进来。

**原则：遇到非法输入要拒绝，不要试图“修正”它。** 比如把 `//` 合并、去掉开头的 `/`，看起来是宽容，实际上是在帮攻击者把恶意路径洗成合法路径。不确定的输入一律拒绝，最简单，也最不容易出错。

另外两类规则属于**兼容性**而不是安全：禁用字符（`\ : * ? " < > |` 和控制字符）、以空格或 `.` 结尾、Windows 保留名（`CON`、`NUL`、`COM1` 等）。这些文件名在 Windows 上无法创建，题库导出后会解压失败。

## 3. 为什么用 `ZipFile` 而不是 `ZipInputStream`？

ZIP 文件里，每个文件的信息记录在两个地方：

- 每个文件数据前面的**本地头**；
- 文件末尾的**中央目录**，汇总了所有文件的名称、大小和 CRC。解压软件以它为准。

| | `ZipFile` | `ZipInputStream` |
| --- | --- | --- |
| 读的是 | 中央目录（权威） | 本地头，从前往后流式读取 |
| 需要 | 文件在磁盘上（上传时先存成临时文件） | 只要一个输入流 |
| 读取前知道 CRC 和大小吗 | 知道 | 不一定。本地头可以不写，放到数据后面的“数据描述符”里，此时 `getCrc()`、`getSize()` 返回 `-1` |

选择 `ZipFile` 的原因：

1. **检查的和实际用的必须是同一份信息。** 攻击者可以故意让本地头和中央目录不一致：`ZipInputStream` 看到的是一套内容，用户本地的解压软件看到的是另一套。用 `ZipFile` 读中央目录，与其他解压软件的视角一致。
2. 中央目录里一定有 CRC，所以读到 `-1` 可以直接判为不合法。

CRC32 的作用是**发现数据损坏**，不能防恶意篡改：攻击者改了数据可以顺手改 CRC。防篡改要用 SHA-256 这样的密码学哈希（内容寻址存储就是这样做的，见 ADR-007）。

## 4. 为什么查重要先转小写，并且用 `Locale.ROOT`？

**转小写查重：** Windows 和 macOS 的文件系统默认不区分大小写。如果包里同时有 `Bank.json` 和 `bank.json`，用户导出或下载题库后在本地解压，后一个会覆盖前一个。攻击者也能利用这一点：让服务器检查的是一个文件，用户本地实际用的是另一个。所以大小写不同也算重复。

**`Locale.ROOT`：** 不传参数的 `toLowerCase()` 使用服务器所在系统的语言设置。在土耳其语环境下，`"I".toLowerCase()` 得到的是 `"ı"`（没有点的 i），而不是 `"i"`，于是 `BANK.json` 和 `bank.json` 转换后不相等，查重就漏过去了。同一份代码换一台服务器，行为就变了。`Locale.ROOT` 表示不依赖任何语言，结果在任何环境下都一样。M1 中 `normalizeEmail` 用 `toLowerCase(Locale.ROOT)` 也是同一个原因。

## 5. 其他设计点

- **快速失败：** 导入流程中，便宜的检查放在前面（大小、路径、格式），贵的放在后面（调用 rule-runner）。解压炸弹在第一步就被拦下，不会消耗 rule-runner 的资源。
- **异常分层：** `ArchiveRejectedException` 是领域异常，分为 `INVALID`（对外 422）和 `LIMIT`（对外 413），由接口层转换成 HTTP 错误。领域层不依赖 HTTP。
- **只捕获该捕获的异常：** `read` 只把 JDK 抛出的 `IOException` 转成“压缩包损坏”。自己抛出的 `ArchiveRejectedException` 是 `RuntimeException`，会直接穿过 `catch`，否则“超过上限”（413）就会被错误地改写成“压缩包损坏”（422）。
- **调用方式：** 读取结果通过回调 `EntryHandler` 逐个交给调用方，而不是一次性返回包含全部文件的集合，调用方可以边读边处理（例如直接写入文件存储）。

## 6. 踩过的坑

- **读出了内容却忘了交给 `handler`**：编译通过、运行不报错，但整个功能什么都没做。这种 bug 只有测试能发现。
- **顶层检查比较了整条路径**：`name.equals("question-banks")` 让所有正常文件都被拒绝。“在某目录下”要看第一段 `parts[0]`，“恰好是某文件”才比较整条路径。
- **保留名用 `matches()` 匹配整条路径**：`question-banks/CON/bank.json` 整体不等于 `CON`，于是漏过。禁用字符、保留名都要逐段检查。
- **`isBlank()` 与 JavaScript `trim()` 的空白集合不同**：Java 的 `isBlank()` 不认不换行空格 `U+00A0`、`U+202F`、`U+2007` 和 `U+FEFF`，只由这些字符组成的段被放行了。移植规则时，“空白”“大小写”“字符”这类概念在两种语言里可能不一样，要按旧版的定义显式写出来。
- **漏了“声明大小 ≠ 实际大小”的检查**：只查上限和 CRC 时，声明 1 字节、实际 64 字节的条目能通过。这条检查放在读完之后，不能代替循环里的实时计数：两条检查有先后顺序，防资源耗尽的必须最先触发。加入后，原先“两个文件都伪造大小”的测试会先被大小检查拦下，测试也要按新顺序调整。
- **改了文件却没有 `git add`**：`git push` 显示 `Everything up-to-date`，远程却没有变化。推送后用 `git log --oneline -1` 确认提交带着 `origin/...`。
- **`find()` 与 `matches()`**：查“是否包含”禁用字符用 `find()`，查“整段是否为”保留名用 `matches()`。
