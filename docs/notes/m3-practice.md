## 1. 写入粒度：每人每题一行

- 旧系统一个用户的一本题库存成一个 JSON 文件，保存任何一道题都要锁住整个文件、读出全部、写回全部，所有保存只能排队。
- V2 把作答拆成每人每题一行（`practice_question_state`，主键 `(context_id, question_id)`）。不同用户、不同题目的保存操作不同的行，天然互不阻塞。**这是性能提升的来源。**
- 不能更细：一道题的作答结构由拓展定义，平台无法拆分；小题进度由 `validateAnswer` 算出，存在同一行的 `outline_states` 中。
- 保存草稿刻意不更新存档行（`practice_context.progress_version`），避免最频繁的操作争抢同一行。

## 2. 乐观锁

```sql
UPDATE practice_question_state SET answer = ?, revision = revision + 1, status = 'draft', updated_at = ?
 WHERE context_id = ? AND question_id = ? AND user_id = ? AND revision = ? AND status <> 'submitted'
```

- 读题时拿到 `revision`，写入时带回来；影响 1 行成功，影响 0 行返回 409。**它不能防止冲突发生，而是发现冲突并拒绝基于过时数据的写入，保证不会悄悄覆盖。** 先提交的赢，后到的必须先看到最新内容再决定。
- 能防：多设备 / 多标签页、请求乱序（旧请求晚到）、评分期间作答被改、作者更新与保存并发。
- **检查和修改必须在一条 SQL 里**。先 `SELECT revision` 在 Java 里比较再 `UPDATE`，两个请求会从中间的缝隙插进来（先查后改竞态）。同一行上的两个 `UPDATE` 由 InnoDB 行锁保证一先一后，后者用最新数据重新判断 `WHERE`。
- `WHERE` 里要放**所有“允许修改”的前提**，不只是版本号：漏了 `status <> 'submitted'`，已提交的题就能被草稿改掉，作答和分数对不上。
- 乐观锁与悲观锁：冲突少用乐观锁（不加锁、失败重试），冲突多用悲观锁（`SELECT … FOR UPDATE` 先锁再改）。保存草稿冲突极少、频率极高，所以用乐观锁。
- 提交时在开始和结束各检查一次版本号：评分在事务外进行（可能几百毫秒），结束时的条件更新保证“评分用的作答”和“写入的作答”是同一份。

## 3. 第一次保存的死锁（间隙锁）

最初写法是“先 UPDATE，影响 0 行再 INSERT”。并发测试发现两个请求同时第一次保存同一题时会死锁：

```text
A：UPDATE 不存在的行 → REPEATABLE READ 下在索引间隙上加间隙锁
B：UPDATE 同一个不存在的行 → 也加间隙锁（间隙锁彼此兼容）
A：INSERT → 需要插入意向锁，被 B 的间隙锁阻塞
B：INSERT → 需要插入意向锁，被 A 的间隙锁阻塞 → 死锁
```

间隙锁的作用是防止幻读：在 REPEATABLE READ 下，已经检查过的范围不允许别人插入新行。

修法：按客户端版本号分支。版本号为 0（读题时还没有作答）只 `INSERT`，主键冲突返回 409；大于 0 只 `UPDATE`。两个并发 `INSERT` 不会死锁：后者等待前者提交后得到主键冲突。另一种修法是把隔离级别降为 READ COMMITTED（没有间隙锁），但会影响整个系统，所以选择改逻辑。

## 4. IDOR：插入时必须检查存档归属

- `user_id` 来自服务器端会话，无法伪造；`context_id` 由客户端提交，可以随意修改。
- `UPDATE` 的 `WHERE user_id = ?` 保护了已有行，但 `INSERT` 没有 `WHERE`：其他用户可以拿别人的存档 ID 插入一行，占住主键 `(context_id, question_id)`，让对方这道题永远无法保存。
- 这类漏洞叫 **IDOR**（不安全的直接对象引用），属于 OWASP“访问控制失效”。修法是让归属检查和写入在同一条 SQL 里完成：

```sql
INSERT INTO practice_question_state (…)
SELECT …, 1, …, 'draft', … FROM practice_context WHERE id = ? AND user_id = ?
```

插入 0 行即存档不属于该用户，返回 409。

- 原则：身份只来自服务器端会话；客户端提交的每个 ID 都要校验归属；不能依赖 ID 难猜（UUIDv7 的前半部分是时间戳，ID 也会通过截图、日志泄露）。
- 主键 `(context_id, question_id)` 不含 `user_id`，前提是“一个存档只属于一个用户”。这条设计假设必须在写入源头强制保证。

## 5. 数据库设计方法（从零推导练习）

1. 写功能：用户要做什么；
2. 挑名词：候选的表（能用一列表示的不单独建表）；
3. 理关系：两个方向都要问；一对多在“多”的一方加外键列；多对多用中间表（中间表常常长出自己的属性，如“我的题库”的名称和分组）；一对一可以合并成列（版本与审核）；
4. 按归属和变化拆：共享 / 私有、不变 / 常变、大 / 小分开（题目与作答分开、白板单独成表、历史冻结快照单独成表）；**拆分是默认，冗余是针对具体查询的优化**（例如分数写入作答表）；
5. 列高频 SQL，反推主键和索引：复合索引遵守**最左前缀**规则，`(context_id, question_id)` 能服务“按存档查全部题”，反过来就不能；InnoDB 按主键顺序存储，同一存档的作答在磁盘上相邻；
6. 并发与约束：版本号、唯一键、回执；
7. 历史单独存：冻结快照；
8. 用并发测试和压测验证，再调整。

## 6. 踩过的坑

- **两个 bug 在第一次实现里都没有暴露**：普通单元测试只验证串行情况，死锁和 IDOR 都是并发测试和越权测试找出来的。
- **在 `catch (Exception e)` 里返回 409**：数据库故障、SQL 写错都会被伪装成“请刷新”，问题被隐藏。只捕获 `DuplicateKeyException`。
- **VS Code 快速修复生成的空方法**：调用不存在的 `ApiException.conflict(...)` 时，快速修复生成了一个只抛 `UnsupportedOperationException` 的方法，编译错误消失，问题却没解决。
- **在旧结构上打补丁**：修复要求改变判断顺序时，在原有结构上加 `if` 往往不够，应按新的决策树重新组织。
- **测试与实现耦合**：并发测试的辅助类只拦截 `updateDraft`，实现改为直接 `INSERT` 后闸门不再触发，测试失败。测试依赖“执行了哪些 SQL”时，实现改变要同步调整测试。
- **Git**：在 `main` 上提交、在 `backend` 目录下 `git add backend/src` 路径不匹配、分支被另一个 worktree 占用。提交前看一眼当前分支和当前目录。
