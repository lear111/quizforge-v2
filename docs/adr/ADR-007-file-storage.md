# ADR-007：文件存储使用本地磁盘与内容寻址，私有文件由 Java 授权、Nginx 发送

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-06、FR-07、NFR-07、需求 4.3 节“资源与业务解耦”
- 相关文档：[总体架构 4.1、4.6、5.3 节](../architecture/01-overview.md)、[遗留契约 C-01、F-01](../legacy/01-contracts.md)

## 背景

V2 需要存放的文件有：

| 类别 | 例子 | 大小 | 谁能访问 |
| --- | --- | --- | --- |
| 题库包 | 上传到 Hub 的 `.qbank` | ≤ 64 MiB | 公开已审核的人人可下载；未审核的仅作者与管理员可下载 |
| 题库附件 | `assets/` 图片（≤ 4 MiB）、`media/` 听力音频（单段 ≤ 8 MiB） | 中小 | 导入了该题库的用户 |
| 拓展包文件 | 拓展的 HTML、JS、CSS、规则、Schema | 小 | 前端（内联进沙箱 iframe）、rule-runner |
| 用户上传 | 作答中的图片（`POST /api/resources`） | ≤ 4 MiB | 仅本人 |
| 手写草稿 | 白板笔迹数据 | 不定 | 仅本人 |
| 历史快照中的页面资源 | 冻结的拓展页面 | 小 | 仅本人 |
| Hub 截图、安装包 | 题库截图、Windows / Android 安装包 | 截图小、安装包大 | 公开 |

需要决定三件事：文件**存在哪里**、**如何命名和组织**、**如何安全高效地发给浏览器**。

### 旧系统的做法（仅作参考）

- 题库附件放在每个用户工作区的目录里：同一本题库被 17 个人导入，就有 17 份副本。
- 图片按 SHA-256 命名（`assets/<sha256>.<ext>`），这一点很好。
- 所有资源请求都经过练习服务的全局排队和整份备份（`hub/cloud/practice.mjs`），所以下载一张图片也要排队。
- 前端读取听力音频时，是用 `fetch` 下载**整个文件**后再生成 Blob URL 播放（`LISTENING.md`）。这样做的原因是本地版的认证放在请求头里，`<audio src>` 无法携带。它的代价是无法流式播放，也无法使用 HTTP Range。

## 决策驱动因素

1. **不影响答案保存（需求 4.3）：** 传输大文件不能占用处理动态请求的 Java 线程。
2. **权限不能因优化而泄露（FR-06）：** 私有文件即使走了缓存或静态服务，也只能被有权限的用户拿到。
3. **支持缓存和 Range（FR-06）：** 音视频要能流式播放、拖动进度条。
4. **简单：** 一台服务器、17 个现有用户，不应为文件存储引入额外的分布式系统。
5. **以后能换：** 用户增长后可以平滑换成对象存储。

## 备选方案

### 存储位置

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 服务器本地磁盘 | 文件放在挂载的目录中 | 最简单，单机足够；需要自己做备份 |
| B. 对象存储（MinIO 自建 / 云 OSS、S3） | 通过 S3 协议存取 | 容量和可靠性好，支持预签名 URL；但多一个组件或一笔云费用，目前规模不需要 |
| C. 存进 MySQL（BLOB） | 文件与数据放在同一个库 | 数据库体积膨胀，备份变慢，传输占用数据库连接。**排除** |

### 发送方式

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| 1. Java 读取文件后写给浏览器 | Spring 的 `ResourceRegion` 也能支持 Range | 实现简单，但大文件传输期间一直占用 Java 线程，违反驱动因素 1 |
| 2. Java 授权 + Nginx 发送（`X-Accel-Redirect`） | Java 检查权限后，只返回一个响应头告诉 Nginx 发哪个文件；文件由 Nginx 发送 | Java 只做一次很快的权限判断；Range、缓存、断点续传由 Nginx 原生支持 |
| 3. 公开文件由 Nginx 直接发送 | 无需任何判断 | 只适用于公开文件 |
| 4. 预签名 URL（对象存储） | Java 签发一个短期有效的链接 | 与方案 B 配套使用，以后再考虑 |

## 决策

**存储位置：方案 A，服务器本地磁盘。所有业务代码通过 `FileStorage` 接口访问文件，以后可以替换为方案 B。**

**命名方式：内容寻址。** 文件以内容的 SHA-256 命名，相同内容只存一份。

**发送方式：**

- **公开文件**（已审核题库的截图、安装包、前端静态页面）：由 Nginx 直接发送。
- **私有文件**（题库附件、用户上传、草稿、未审核题库包）：浏览器请求 Java 的接口，Java 检查权限后返回 `X-Accel-Redirect`，由 Nginx 从内部位置发送文件。

### 目录布局

```text
/data/quizforge/files/              （挂载到宿主机，app 读写，nginx 只读）
├── blobs/sha256/ab/cd/abcd…ef      所有内容寻址文件：题库附件、拓展文件、用户上传、草稿、快照资源
├── packs/<packId>/<revision>.qbank Hub 题库包（按版本保存，不可变）
├── public/                         公开文件：截图、安装包
└── tmp/                            上传与解压的暂存区，定期清理
```

- `blobs/` 按哈希前两段分子目录，避免单个目录中文件过多。
- 文件一旦写入就**不再修改**；内容变化即生成一个新文件。所以缓存永远不会过期失效。
- 写入流程：先写到 `tmp/`，边写边计算 SHA-256，校验大小，然后原子重命名到 `blobs/`；目标已存在就直接丢弃临时文件（自然去重）。
- 拓展包展开后也存入 `blobs/`，由数据库记录“拓展摘要 → 文件清单”的对应关系。rule-runner 以只读方式挂载 `blobs/`（ADR-003）。

### 权限模型

文件本身没有“主人”，**权限来自数据库中的引用关系**：

- **题库附件：** 用户拥有某个题库实例，而该实例的题库内容引用了这个哈希，则允许访问。
- **用户上传、草稿：** 只有上传者本人。
- **数据库记录引用，文件只是内容。** 同一个文件被多个用户的题库引用时只存一份，但每个用户只能通过自己的引用访问它。

Java 的权限检查是按索引查询一次引用表，完成后返回：

```http
HTTP/1.1 200 OK
X-Accel-Redirect: /internal-files/blobs/sha256/ab/cd/abcd…ef
Content-Type: image/png
Cache-Control: private, max-age=31536000, immutable
```

Nginx 中的内部位置只能由 `X-Accel-Redirect` 触发，浏览器无法直接访问：

```nginx
location /internal-files/ {
    internal;
    alias /data/quizforge/files/;
}
```

### 缓存

- 私有文件：`Cache-Control: private, max-age=31536000, immutable`。只允许浏览器自己缓存，代理和 CDN 不得缓存。内容寻址保证文件内容永远不变。
- 公开文件：`public` 长期缓存。
- 前端静态资源：文件名或 URL 带版本，长期缓存；`index.html` 不缓存。

### 对复用前端的配套修改

- **听力音频改为直接使用 `<audio src="/api/...">`。** V2 改用 Cookie 认证（ADR-005）后，浏览器在请求 `<audio src>` 时会自动带上 Cookie，不再需要先下载整个文件再生成 Blob URL。这样音频可以流式播放，并通过 Range 拖动进度。这是 ADR-006 改造清单中的一项。
- 图片仍按旧方式通过 `fetch` 读取并内联进拓展 iframe（沙箱中的 iframe 不能自己发请求，C-02），由于有浏览器缓存，重复访问时不会重新下载。

### 外部 URL 资源（FR-07）

旧版题库目前不支持外部 URL 资源（`LISTENING.md` 规定只能引用题库内的文件）。如果以后支持：

- 平台只对 URL 做安全校验（只允许 `https`、域名格式合法、禁止指向内网地址），**不代理、不下载、不缓存**第三方文件，由浏览器直接请求；
- 不承担第三方的速度与可用性（需求 FR-07）。

具体协议另行提出需求变更。

## 后果

**正面：**

- 文件传输完全不占用 Java 线程，满足“资源与业务解耦”。
- Range、缓存、断点续传由 Nginx 原生实现，不需要自己编写。
- 内容寻址天然去重：一本题库无论多少人导入，附件都只存一份。旧系统中每人一份副本的问题随之消失。
- 文件不可变，缓存策略极其简单。

**负面：**

- 单机磁盘没有冗余，**必须做备份**（与 MySQL 备份同步进行，详见运维设计）。备份时须保证数据库与文件的一致性：先备份数据库，再备份文件；由于文件只增不改，这个顺序不会出现“数据库引用了不存在的文件”。
- 文件不会因为引用删除而立即删除，需要一个**垃圾回收任务**定期清理不再被任何记录引用的文件。
- 本地开发也需要配置 Nginx 才能测试 `X-Accel-Redirect`。可以在开发环境中改为由 Java 直接发送（通过配置开关切换）。

## 如何验证

1. **权限测试：** 用户 A 尝试读取只有用户 B 题库引用的附件，必须返回 404；直接访问 `/internal-files/...` 必须返回 404。
2. **Range 测试：** 对音频发送 `Range: bytes=1000-1999`，返回 `206` 及正确的内容；在浏览器中拖动播放进度条正常。
3. **去重测试：** 两个用户导入同一本题库后，`blobs/` 中的附件文件数量不变。
4. **解耦测试：** 压测时让 100 个虚拟用户持续下载音频，同时测量答案保存接口，保存的 P95 仍满足 NFR-03。
5. **资源并发测试：** 按验收场景 2 测量网络吞吐、失败率、缓存命中和 Range 行为，并记录服务器出口带宽。

## 面试要点（自用）

- 为什么不让 Java 直接发文件：线程被慢速下载长时间占用，影响其他请求。
- `X-Accel-Redirect` 的工作原理，以及它如何同时做到“权限由应用控制、传输由 Nginx 负责”。
- 内容寻址的好处：去重、不可变、缓存简单；代价是需要垃圾回收。
- `private` 与 `public` 缓存的区别，以及为什么私有文件不能被 CDN 缓存。
- 如何平滑迁移到对象存储：`FileStorage` 接口加上预签名 URL。
