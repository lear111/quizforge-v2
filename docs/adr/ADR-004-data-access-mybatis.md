# ADR-004：数据访问使用 MyBatis

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-04、NFR-05、NFR-06、NFR-10
- 相关决策：[ADR-002 MySQL](ADR-002-database-mysql.md)

## 背景

ADR-002 确定使用 MySQL。接下来要决定 Java 代码**如何读写数据库**，也就是持久层框架的选型。

V2 的数据访问有以下特点：

- **大部分是简单的增删改查：** 按 ID 查、按用户分页查。
- **少数关键写操作对 SQL 的精确性要求很高**（来自 ADR-002 的设计约定）：
  - 乐观锁更新：`UPDATE answer SET ..., version = version + 1 WHERE id = ? AND user_id = ? AND version = ?`，根据影响行数判断是否冲突；
  - 幂等插入：依赖唯一约束，`INSERT ... ` 冲突时识别为重复提交；
  - 题目数据、作答内容存放在 `JSON` 列中，整体读写。
- **每条私有数据的查询都必须带 `user_id` 条件**（NFR-06），最好能直接在 SQL 中看出来。
- **性能要可分析：** 压测时需要知道每个接口实际执行了哪些 SQL，并能用 `EXPLAIN` 分析。

## 决策驱动因素

1. **SQL 透明可控：** 关键写操作的 SQL 必须是开发者写的那一条，而不是框架推断出来的。
2. **便于审查用户隔离：** 审查代码时能直接看到每条查询是否带了 `user_id`。
3. **性能可预测：** 没有隐藏的懒加载和意外的多次查询（N+1 问题）。
4. **学习与面试价值：** 国内 Java 后端岗位普遍使用 MyBatis，同时也常考察 JPA。
5. **开发效率：** 简单的增删改查不应过于繁琐。

## 备选方案

### 方案 A：Spring Data JPA（Hibernate）

用注解把 Java 实体类映射到表，大部分查询由框架根据方法名自动生成。

- 优点：
  - 简单增删改查几乎不用写 SQL，开发快。
  - 内置乐观锁（`@Version`）和审计字段。
  - 国际上使用广泛。
- 缺点：
  - SQL 由框架生成，关联关系一多，容易出现懒加载异常和 N+1 查询，排查需要对 Hibernate 有较深理解。
  - 实体被修改后会在事务结束时自动写回数据库（脏检查），写操作不够显式。
  - `JSON` 列的映射需要额外配置或第三方库。
  - 用户隔离条件分散在方法名和注解中，审查不如直接看 SQL 直观。

### 方案 B：MyBatis

SQL 由开发者显式编写（注解或 XML），MyBatis 负责参数绑定和结果映射。

- 优点：
  - **每一条 SQL 都是显式的。** 乐观锁、幂等插入、`user_id` 过滤一目了然，便于审查和用 `EXPLAIN` 调优。
  - 没有懒加载和脏检查，读写行为可预测。
  - `JSON` 列可以通过自定义 `TypeHandler` 统一处理。
  - 国内使用最广，资料多。
- 缺点：
  - 简单增删改查也要写 SQL，代码量比 JPA 多。
  - 改表结构时需要手动同步相关 SQL，靠测试来发现遗漏。

### 方案 C：MyBatis-Plus

在 MyBatis 基础上提供通用增删改查、分页、乐观锁插件等，国内非常流行。

- 优点：保留 MyBatis 写 SQL 的能力，又减少了简单增删改查的代码。
- 缺点：通用方法和条件构造器（`QueryWrapper`）会让一部分 SQL 重新变得隐式，用户隔离条件容易被遗漏；插件机制增加了额外的理解成本。

### 方案 D：Spring JDBC（`JdbcClient` / `JdbcTemplate`）

直接写 SQL，手动映射结果。

- 优点：最轻量，没有额外概念，SQL 完全透明。
- 缺点：结果映射和动态 SQL（如可选的筛选条件）需要手写，模块和表一多会比较繁琐。

## 决策

**采用方案 B：MyBatis（官方 `mybatis-spring-boot-starter`），暂不引入 MyBatis-Plus。**

V2 中最重要的数据操作（并发保存、幂等提交、用户隔离）都要求 SQL 精确、可审查，这正是 MyBatis 的强项。多写一些简单 SQL 的代价可以接受，而且这本身就是学习 SQL 的好机会。

暂不使用 MyBatis-Plus，是为了先把 SQL 和 MyBatis 本身掌握扎实，并保证所有查询都是显式的。若以后简单增删改查的重复代码确实过多，可以另提 ADR 再评估。

### 使用约定（详细设计阶段细化）

| 约定 | 内容 |
| --- | --- |
| SQL 位置 | 简单 SQL 用注解；超过约 5 行或包含动态条件的写在 XML 中 |
| 模块边界 | 每个模块有自己的 Mapper，只访问本模块的表（ADR-001） |
| 用户隔离 | 用户私有数据的 Mapper 方法必须以 `userId` 作为参数，并在 SQL 中使用；由测试检查 |
| 乐观锁 | 更新方法返回影响行数，Service 层判断为 0 时抛出冲突异常，最终返回 409 |
| JSON 列 | 统一的 `JsonTypeHandler`，使用 Jackson 序列化 |
| 禁止事项 | 禁止使用 `${}` 拼接用户输入（防止 SQL 注入），只允许 `#{}` 参数绑定；排序字段等必须使用白名单 |
| 事务 | 事务边界放在 Service 层的 `@Transactional` 上，Mapper 不管理事务 |

## 后果

**正面：**

- 每条 SQL 都可以单独审查和优化，压测发现慢查询时能直接定位。
- 并发控制和用户隔离的实现方式清楚，容易写出针对性的测试。

**负面：**

- 简单增删改查代码量比 JPA 多。
- 表结构变更后，需要通过集成测试发现未同步的 SQL。

## 如何验证

1. **Mapper 集成测试：** 每个 Mapper 用 Testcontainers 启动真实 MySQL 进行测试，覆盖乐观锁冲突（影响 0 行）和唯一约束冲突。
2. **用户隔离测试：** 以用户 A 的身份，用用户 B 的数据 ID 调用每个私有数据接口，结果必须为“不存在”或 403，绝不能返回数据。
3. **SQL 注入检查：** CI 中检查 Mapper 文件，出现 `${` 时必须在白名单中。
4. **慢查询检查：** 压测期间开启 MySQL 慢查询日志，核心接口不应出现全表扫描。

## 面试要点（自用）

- MyBatis 与 JPA 的根本区别：前者以 SQL 为中心，后者以对象为中心。
- 为什么本项目选 MyBatis：关键写操作需要精确的 SQL，用户隔离需要便于审查。
- `#{}` 与 `${}` 的区别，以及 SQL 注入。
- 乐观锁的实现：`version` 列加上影响行数判断。
- 如果让你选 JPA，你会注意什么：N+1、懒加载、脏检查、`@Version`。
