# ADR-008：旧数据采用停机一次性迁移，以接口输出对比验证

- 状态：提议
- 日期：2026-10-27（2026-10-28 修订：迁移范围缩小，见下方“修订”）
- 相关需求：FR-09、C-04、C-05、C-06、NFR-05、NFR-11、验收场景 11
- 相关文档：[旧数据字典](../legacy/02-data-dictionary.md)、[遗留契约 F-01](../legacy/01-contracts.md)

## 修订（2026-10-28，需求 v1.3）

迁移范围缩小为**账号**（含手机号、封禁记录、密码哈希）与 **AI 余额及流水**。题库、拓展白名单、练习工作区（作答、历史、考试）、设备令牌不再迁移。对本 ADR 的影响：

- “停机一次性迁移”（方案 A）保持不变；
- 工作区 JSON 的读取方式（方案 X / Y）**不再需要**，第三层“接口对比验证”随之取消；
- 验证改为：用户数、每个用户的余额等于流水总和且与旧库一致、抽查用原密码登录（含只有手机号的用户）；
- 前置工作中的 D-1（确认生产数据格式代际）仍需完成，但只涉及账号与 AI 相关表；
- 切换时须提前通知用户：练习进度与历史不保留，本地 `.qbank` 须用新版客户端重新导出，客户端须重新授权。

以下为原始决策记录，与修订冲突处以修订为准。

## 背景

V2 上线前，需要把旧在线平台的数据迁移到新系统（FR-09）。要迁移的数据分布在三处（详见旧数据字典）：

1. Java Hub 的 SQLite（账号、题库广场、审核、AI 余额）；
2. Node 练习服务的 SQLite（导入记录、配额、拓展审核白名单）；
3. 每个用户的练习工作区：`bank.json`、拓展文件，以及 `.state/` 中的 JSON 文件（作答、历史轮次、考试、白板）。

已知情况：

- 约 **17 个用户**（2026-10-27）。
- 回收站中的题库、登录会话、验证码等临时数据不迁移。
- 生产环境**仍在运行旧 Node 版 Hub**，尚未切换到 Java Hub（`quizforge_hub/README.md`），生产数据的格式代际需要先确认（数据字典 D-1）。

## 决策驱动因素

1. **已确认保存的数据零丢失**（NFR-05），无法识别的数据不能被静默丢弃（FR-09）。
2. **可验证：** 迁移完成后要能证明“每个用户看到的东西和以前一样”，而不只是“条数对得上”。
3. **可回退：** 发现问题时能回到旧系统继续服务。
4. **与规模相称：** 17 个用户不需要零停机迁移这类复杂方案。
5. **不复用旧服务端源码**（需求第 5 节），但可以把旧系统当作对照的“黑盒”。

## 备选方案

### 迁移方式

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 停机一次性迁移 | 旧系统停写 → 迁移 → 校验 → 切换 | 最简单、最可靠；需要一段停机时间，17 个用户可以提前通知 |
| B. 双写 / 增量同步后切换 | 新旧系统并行运行，持续同步变更，最后瞬间切换 | 停机接近零，但需要实现变更捕获与冲突处理，复杂度高得多。对 17 个用户来说完全不划算 |
| C. 按用户逐个迁移 | 每个用户第一次登录新系统时迁移自己的数据 | 不用统一停机，但新旧系统要长期共存，Windows 客户端和 Hub 链接难以同时指向两边。**排除** |

### 工作区 JSON 的读取方式

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| X. 迁移工具直接解析 `.state/` 文件 | 用 Java 读取 JSON，自己实现格式解析 | 不依赖旧系统运行；但要完整理解每一代历史格式，容易遗漏旧字段 |
| Y. 启动旧系统，通过它的接口读出数据 | 用旧系统的 `GET` 接口取得“已经解码好”的数据 | 旧格式的兼容逻辑由旧系统自己负责；但需要运行旧系统，且接口返回的是投影后的数据，可能缺少内部字段（例如请求回执） |

## 决策

**迁移方式采用方案 A：停机一次性迁移。**

**读取方式以方案 X（直接解析）为主，以方案 Y（旧系统接口）作为验证手段。**

方案 Y 无法取得全部内部字段，不能单独作为迁移来源；但旧系统接口与 V2 的前端接口是**同一套契约**（遗留契约 F-01，ADR-006），这带来一个很好的验证方法：**对同一个用户的同一道题，分别请求旧系统和新系统的接口，比较两边的响应。** 两边一致，就说明用户看到的东西没有变。

### 迁移工具

- 作为 V2 仓库中的一个**独立命令行程序**（Java），不包含在线上应用里。
- 用 JDBC 读取两个旧 SQLite 库，用 Jackson 读取工作区 JSON，通过 V2 的数据访问层（或专用的批量 SQL）写入一个**全新的空** V2 数据库，并把文件复制到 V2 的文件存储（ADR-007）。
- **只读旧数据。** 迁移工具以只读方式打开旧数据的**副本**，绝不修改原件。
- **可重复执行：** 每次都从空库开始；出错时清空目标库重跑，不做“断点续迁”，以免产生半迁移状态。
- 无法识别的数据**不丢弃、不猜测**：记录到迁移报告中，并保留原始文件路径，交由人工处理。

### 三种运行模式

| 模式 | 作用 |
| --- | --- |
| `inspect` | 只读扫描旧数据，输出统计：用户数、题库数、作答数、历史轮次数、文件总大小、识别出的格式代际，以及无法识别的条目。用于回答数据字典中的 D-1、D-6 |
| `migrate --dry-run` | 完整执行转换，但写入一个临时数据库；输出“将迁移 / 将跳过 / 无法识别”的清单 |
| `migrate` | 正式迁移，并生成迁移报告 |

另提供 `verify` 模式执行下面的验证。

### 验证（三层）

1. **数量核对：** 逐表、逐用户核对数量，包括用户、题库实例、每个集合的已作答题数、历史轮次数、AI 余额。
2. **内容核对：**
   - 文件逐个比对 SHA-256；
   - AI 余额必须等于流水总和，并与旧库一致；
   - 拓展审核摘要原样迁入后，用 V2 重新实现的摘要算法（C-04）重新计算并比对。
3. **接口对比（行为一致性）：** 在隔离环境中同时运行旧系统（已停写的副本）与 V2，对**每个用户**的每个题库，请求题库概览、每道题、汇总和历史列表，比较两边的响应。
   - 先规范化可以合理不同的字段（例如内部版本号、时间格式），再比较其余字段；
   - 任何差异都列入报告，必须逐条解释或修复后才能切换。

    17 个用户的数据量很小，这一步可以对**全量**数据执行，而不只是抽样。

### 切换流程（Runbook 要点，详见运维文档）

```text
T-7 天   通知用户维护时间；在生产数据副本上完整演练一次（验收场景 11）
T-0      1. 旧系统切换为只读维护页面（停写）
         2. 确认旧练习服务的 cloud_practice_writes 为空、没有未完成的检查点
         3. 完整备份旧数据（两个库 + 全部工作区 + 附件），记录摘要
         4. 运行 migrate，再运行 verify
         5. 验证通过：Nginx 切到 V2；抽查几个账号用原密码登录、查看历史
            验证不通过：保持旧系统，撤销维护页面，恢复服务
T+30 天  旧系统数据只读保留至少 30 天（FR-09），之后再归档
```

- **回退：** 切换后发现严重问题时，Nginx 切回旧系统。注意，切换后用户在 V2 上产生的新数据**不会自动回流**到旧系统。因此切换后的头几个小时是观察窗口，在此期间发现问题再回退，损失最小。是否需要“回流”工具，视演练结果决定。
- **Windows / Android 客户端：** 设备令牌已迁移（C-05），客户端连接的 Hub 地址不变，切换对客户端透明。

### 先要完成的前置工作

1. 取得一份生产数据副本，用 `inspect` 确认格式代际与规模（数据字典 D-1、D-6）。
2. 如果生产数据属于旧 Node Hub 格式，参考旧系统已有的 Node → Java 升级逻辑（`scripts/snapshot-hub-for-java.mjs`、`HubDatabase.java` 中的结构升级），确认两代表结构的差异。
3. 新数据模型（详细设计）确定后，编写“旧 → 新”字段映射表，作为迁移工具的规格说明。

## 后果

**正面：**

- 流程简单，每一步都可以检查。
- 迁移工具可以反复运行和演练，正式迁移时没有意外。
- 接口对比可以证明“用户体验一致”，这是比计数更强的证据。

**负面：**

- 需要一次停机。数据量很小，预计停机时间主要花在验证上，演练后可以给出准确时长。
- 验证需要临时运行旧系统，因此要保留一个可运行的旧版本（不需要修改它）。
- 迁移工具只用一次，但仍需要认真编写和测试；它的测试数据来自生产副本，**必须脱敏**，且不能提交到 Git。

## 如何验证（本决策本身）

1. 在生产副本上完整演练至少一次，`verify` 三层核对全部通过或差异均有解释（验收场景 11）。
2. 演练中故意制造一处损坏的 JSON，确认它出现在报告中，而不是被跳过或导致整体失败。
3. 演练回退：切换到 V2 后再切回旧系统，旧系统可正常使用。
4. 记录演练的总耗时，作为正式停机时间的依据。

## 面试要点（自用）

- 为什么不做零停机迁移：17 个用户，复杂度与收益不成比例。能说出零停机方案（双写、变更捕获）是怎么做的，以及什么规模下才值得。
- 迁移的三层验证：数量、内容、行为。
- “新旧系统接口契约相同”如何被巧妙地用来做行为对比验证。
- 迁移工具为什么必须可重复执行、只读源数据、从空库开始。
- 回退方案的局限：切换后的新数据不会自动回流，所以观察窗口很重要。
