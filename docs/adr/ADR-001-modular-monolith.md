# ADR-001：采用模块化单体，而不是微服务

- 状态：提议
- 日期：2026-10-27
- 相关需求：需求第 5 节（不提前分布式化）、NFR-01、NFR-10、NFR-11
- 相关文档：[总体架构 4.4 节](../architecture/01-overview.md)

## 背景

V2 后端要承担的业务有：账号与权限、题库广场（上传、审核、发布）、练习（作答、草稿、提交）、考试与历史、资源授权、AI 辅导、后台管理。

需要决定：这些业务是做成**一个应用**，还是**拆成多个独立部署的服务**。

旧系统实际上是两个服务：Java Hub 加 Node 练习服务。两者之间通过回环 HTTP 互相调用（查身份、查 AI 余额、管理桥），并且各有一个 SQLite 数据库，用户表需要在两边同步。这正说明了拆分服务的代价：每多一条服务间调用，就多一个可能失败的地方和一份需要同步的数据。

## 决策驱动因素

1. **规模：** 目标是 100 名活跃用户（估算约每秒 10 次写、20 次读）。一台服务器上的一个 Java 进程完全能承载。
2. **事务一致性：** 一次提交需要同时写作答、提交记录、评分结果，考试交卷还要冻结历史快照。这些写入最好在**一个数据库事务**里完成。
3. **团队规模：** 目前有两名开发者。微服务主要解决的是“多个团队独立开发、独立发布”的问题，通常一个服务由一个 3～8 人的小团队负责。两个人如果维护多个服务，每人要负责好几个服务的部署、监控和接口兼容，协作成本反而增加。两个人需要的是清晰的分工和代码审查流程（见“协作约定”），而不是拆分部署单元。
4. **运维成本：** 每多一个服务，就要多一套部署、日志、监控、配置和版本兼容。
5. **可维护性和以后的演进：** 代码不能写成一团，以后真的需要拆分时，要能拆得动。
6. **面试价值：** 能清楚说明“为什么现在不用微服务、什么情况下才拆”，比盲目使用微服务更有说服力。

## 备选方案

### 方案 A：普通单体（按技术分层）

传统的 `controller / service / mapper` 三个包，所有业务混在每一层里。

- 优点：最简单，上手最快。
- 缺点：没有业务边界。例如练习代码可以直接查询账号表，时间一长各模块互相依赖，改一处牵动多处，以后也拆不开。

### 方案 B：模块化单体

一个应用、一个部署包，但**代码先按业务分模块**，模块内部再分层：

```text
cloud.treenewbee.quizforge
├── identity    账号与权限
├── catalog     题库广场
├── content     题库内容与拓展包：.qbank 解析、校验与存储（无用户数据）
├── practice    练习
├── exam        考试与历史
├── resource    资源授权
├── ai          AI 辅导
├── admin       后台管理
└── shared      通用工具（不放业务逻辑）
```

模块之间的规则：

- 一个模块只能调用另一个模块**公开的接口**（例如 `identity` 对外暴露的 `UserQueryService`），不能使用对方的内部类。
- 一个模块**不直接读写另一个模块的表**，需要对方的数据就调用对方的接口。
- 这些规则通过自动化测试强制检查（见“如何验证”），而不是靠自觉。

- 优点：部署和运维和普通单体一样简单；跨模块的写操作可以在一个事务中完成；业务边界清晰；以后某个模块确实需要独立扩容时（例如 AI），可以沿着已有边界拆出去。
- 缺点：需要一开始就规划模块边界；模块之间依赖接口而不是直接访问，代码会多一些。

### 方案 C：微服务

按业务拆成 4～6 个服务（账号、题库、练习、AI 等），各自独立部署，通常各有自己的数据库，通过 HTTP 或消息队列通信。

- 优点：可以按服务独立扩容和发布；技术栈可以不同；一个服务崩溃不会直接拖垮其他服务。
- 缺点：
  - 跨服务的写操作没有数据库事务，需要分布式事务或最终一致性方案，复杂度大增。
  - 还需要服务发现、网关、链路追踪、配置中心等基础设施。
  - 本地开发和测试要同时启动多个服务。
  - 需求第 5 节明确不提前引入微服务。

### 方案 D：沿用旧的拆分方式（Hub 服务 + 练习服务），用 Java 重写

- 优点：与旧系统的结构对应，迁移时比较直观。
- 缺点：保留了旧系统中“服务间回环调用 + 两份数据库 + 用户表同步”的问题。这次拆分只是历史原因（练习服务要复用 Web 内核）造成的，并没有业务上的理由。

## 决策

**采用方案 B：模块化单体。**

100 人的规模、两人团队和强事务需求，都不需要微服务；而方案 A 的问题会在项目变大后出现。模块化单体的运维成本和单体一样，又保留了以后拆分的可能。

### 协作约定（两名开发者）

> 当前 V2 由一人开发，另一名开发者维护旧版（AI 模块）。以下约定中，分支保护与 PR + CI 流程从现在开始执行；模块分工与交叉审查在第二名开发者加入 V2 时生效。

- **按模块分工：** 每个模块有明确的负责人，具体分配在项目启动时商定，并记录在仓库根目录的 `CODEOWNERS` 中。改动他人负责的模块时，PR 自动请求对方审查。
- **保护 main 分支：** 禁止直接推送；所有改动通过 PR 合并，需至少一名他人审查通过且 CI 全部通过。
- **跨模块接口变更：** 修改模块的公开接口时，须在 PR 中说明影响，并由被影响模块的负责人审查。
- **模块边界测试：** 防止两人的代码在不知不觉中互相依赖（见“如何验证”第 1 条）。

**唯一的例外是规则执行服务（rule-runner）。** 它独立部署，原因不是业务拆分，而是语言和安全隔离（见 [ADR-003](ADR-003-extension-rule-execution.md)）。它不保存任何数据，所以不会带来跨服务的数据一致性问题。

### 什么时候考虑拆分

满足以下任一条件，并有压测或监控数据支持时，再提出新的 ADR：

- 某个模块的资源消耗明显影响其他模块，且无法通过线程池隔离解决（AI 模块是最可能的候选）。
- 需要比单台服务器更高的容量，且水平扩展整个应用不经济。
- 出现多个团队需要独立发布不同模块的情况。

## 后果

**正面：**

- 一个部署包、一个数据库，部署、调试和测试都简单。
- 提交、交卷等跨模块写入可以用一个 `@Transactional` 保证一致。
- 代码结构按业务组织，阅读代码时能直接对应需求文档。

**负面：**

- 所有模块共享一个 JVM。某个模块的内存泄漏或线程耗尽会影响全部模块，需要靠线程池隔离（例如 AI 使用独立线程池，见总体架构 4.8 节）和监控来缓解。
- 任何一个模块的修改都需要重新部署整个应用。在当前规模下这不是问题。

**要求：**

- Java 应用必须**无状态**：会话存数据库，不在内存里保存用户状态（见 ADR-005）。这样在需要时可以启动第二个实例，用 Nginx 做负载均衡，不必拆服务。

## 如何验证

1. **模块边界测试：** 引入 [Spring Modulith](https://spring.io/projects/spring-modulith) 或 ArchUnit，编写测试检查“模块只能依赖其他模块的公开接口”“不存在模块间循环依赖”，并纳入 CI；违反规则则构建失败。
2. **单实例压测：** 阶段六的 100 人混合负载测试只运行一个 Java 实例，验证单体能满足 NFR-01～NFR-04 和 NFR-08。
3. **无状态检查：** 在压测过程中重启 Java 应用，已登录用户在重启后无需重新登录，已确认保存的数据不丢失。

## 面试要点（自用）

- 微服务主要解决组织问题（多团队独立交付），其次才是技术问题；两人项目使用微服务，主要会带来分布式事务和运维成本。小团队协作靠的是模块所有权、代码审查和 CI，而不是拆分部署。
- “模块化”通过自动化测试强制执行，而不是只体现在目录名上。
- 能说出拆分的触发条件，说明这是一个可以演进的决定。
- 旧系统为什么拆成两个服务、带来了哪些问题，是现成的反面案例。
