# ADR-009：Redis 用于 AI 短期对话记忆与限流计数

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-08（AI 辅导）、第 4 节安全约束、需求第 5 节（不提前引入无依据的组件）
- 相关决策：[ADR-001](ADR-001-modular-monolith.md)（应用无状态）、[ADR-005](ADR-005-session-auth.md)（会话存数据库）

## 背景

两类数据有共同特点：**短期有效、过期即丢弃、读写频繁、丢失后果轻微，但不能只放在应用内存里**。

1. **AI 辅导的短期对话记忆（FR-08）。** 用户可以对当前题目连续追问，模型需要看到同一题之前的几轮对话。需求明确第一阶段**不做**长期记忆，切换题目后旧对话就没用了。
2. **限流计数。**
   - 登录与验证码：防止暴力破解；
   - AI 调用：每次调用都要花钱（FR-08 要求有额度与频率限制）。

   旧系统把这些计数放在进程内存中（`practice/server.mjs` 的 `limits` Map）。**应用一重启，计数就清零**，攻击者等到重启后就能继续尝试；AI 的频率限制也会失效。

这两类数据目前有三种存放方式可选：应用内存、MySQL、Redis。

## 决策驱动因素

1. **应用无状态（ADR-001）：** 重启不能让限流失效；以后运行多个实例时，计数要在实例之间共享。
2. **自动过期：** 对话和计数都有天然的生存期，最好由存储自动清理。
3. **不给 MySQL 增加无谓负担：** 限流计数在每次请求时都要更新，写入频繁。
4. **与规模相称：** 不为 Redis 本身引入额外的复杂度（集群、持久化调优）。

## 备选方案

| 方案 | 评价 |
| --- | --- |
| A. 应用内存 | 最简单，但重启即丢，也无法在多实例之间共享。**不满足驱动因素 1** |
| B. MySQL | 可行，但每次请求都更新计数行会产生大量小事务，还要自己写过期清理任务；对话这种“用完即弃”的数据也不值得持久化 |
| C. Redis | `INCR` + `EXPIRE` 是限流的标准做法，原子且自带过期；对话列表用 `LIST` 加过期时间。重启应用不影响，多实例天然共享 |

## 决策

**采用方案 C：引入单节点 Redis，只用于以下两个场景。**

| 场景 | 数据结构 | 键 | 过期时间 |
| --- | --- | --- | --- |
| AI 对话记忆 | `LIST`，每项为一轮问答（JSON），只保留最近 N 轮（`LTRIM`） | `ai:conv:{userId}:{contextId}:{questionId}` | 最后一次提问后 2 小时（初值） |
| 限流计数 | 固定窗口：`INCR` 后若为 1 则 `EXPIRE`；或使用 Lua 脚本保证两步原子 | `rl:{场景}:{主体}:{窗口}`，例如 `rl:login:ip:<哈希>:202610271530` | 窗口长度 |

**明确不用 Redis 的地方（及原因）：**

| 不用于 | 原因 |
| --- | --- |
| 登录会话 | 需要立即撤销，且已在 MySQL 中按主键查询，足够快（ADR-005） |
| 读题投影缓存 | 内容不可变，应用内缓存（Caffeine）没有一致性问题，而且更快；不需要跨实例共享 |
| 作答、历史等业务数据 | 必须可靠持久化与事务，只放 MySQL（ADR-002） |
| 分布式锁 | 当前的并发控制都由数据库行锁和乐观锁完成，不需要 |

### 可用性与降级

Redis 中的数据都**可以丢失**，所以 Redis 故障时：

- **AI 对话记忆**：退化为“没有上下文的单轮问答”，AI 辅导仍可使用，只是不记得前几轮。
- **限流**：退化为应用内存计数（单实例下仍有效），并记录告警。**不能因为 Redis 不可用而关闭限流**，也**不能因此拒绝所有登录**。
- 刷题、保存、提交完全不依赖 Redis。

部署上使用单节点 Redis（Docker Compose 中一个容器），**关闭持久化**（数据本来就可以丢），设置最大内存与 `allkeys-lru` 淘汰策略，防止内存无限增长。

## 后果

**正面：**

- 限流在应用重启后依然有效，满足安全要求。
- 对话记忆自动过期，不需要清理任务。
- 应用保持无状态，以后多实例部署时无需改动。

**负面：**

- 部署中多一个组件，需要监控其内存与可用性。
- 需要实现上面的降级逻辑，并为它写测试。

## 如何验证

1. **限流测试：** 同一 IP 连续登录失败超过阈值后返回 429；**重启应用后仍然返回 429**，直到窗口结束。
2. **对话测试：** 同一题连续追问时，模型请求中包含前几轮对话；切换题目后不包含；超过过期时间后对话消失。
3. **降级测试：** 停掉 Redis，AI 辅导仍可单轮问答；登录限流退化为内存计数；刷题功能不受任何影响。
4. **内存测试：** 压测中观察 Redis 内存稳定，不持续增长。

## 面试要点（自用）

- 为什么会话不放 Redis：需要立即撤销，数据库主键查询已经够快，没有必要多一个一致性来源。
- 固定窗口与滑动窗口限流的区别；`INCR` 和 `EXPIRE` 分两步执行时的原子性问题，以及用 Lua 脚本解决。
- Redis 的数据为什么可以丢、丢了怎么降级：这是“把 Redis 当缓存还是当数据库”的根本区别。
- 为什么关闭持久化、为什么用 `allkeys-lru`。
