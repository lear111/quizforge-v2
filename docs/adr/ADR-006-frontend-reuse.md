# ADR-006：复用旧 Web 前端，以源码分叉方式改造

- 状态：提议
- 日期：2026-10-27
- 相关需求：需求第 1 节（v1.1，前端可复用）、FR-03、FR-05、C-02、NFR-09
- 相关文档：[总体架构 4.2、4.3 节](../architecture/01-overview.md)

## 背景

V2 后端重新实现，但旧的浏览器前端在功能和交互上已经比较成熟（题库、作答、草稿与手写、历史、考试、听力、拓展 iframe 宿主等），而且旧系统的多用户问题出在后端，不在前端。因此决定复用前端，不重做（需求 v1.1）。

需要进一步决定：**怎么复用**。

### 旧前端的现状（`quizforge_web/core/web` @ `4522bb8`）

- 原生 JavaScript ES 模块，没有 React / Vue 等框架，页面不需要构建；只有富文本组件（`core/shared/richtext`）有单独的打包脚本。
- 共 57 个 JS 文件、15 个 CSS 文件，入口是 `index.html` 和 `app.js`。
- 与后端的所有交互都经过 `shared/api.js` 中的 `request()` 函数，调用的接口约三四十个（`/api/collections/...`、`/api/library/...`、`/api/resources/...` 等），在 `core/docs/reference/API.md` 的 “HTTP contract” 一节中有说明。
- 认证方式是本地版的远程访问密码：令牌放在 `sessionStorage` 中，通过 `X-QuizForge-Token` 请求头发送。
- 包含一些在线版不需要的本地功能：网络连接设置、开发者设置、本机 AI 配置、本机登录窗口等。

旧 Hub 的 Java 部分还有一套题库广场页面（`java-hub/src/main/resources/static`），同样是原生 JS。

### 旧 Hub 是怎么复用的（反面经验）

旧 Hub 没有修改前端源码，而是在**运行时对固定版本的文件做字符串替换**（`quizforge_hub/cloud/practice-ui.mjs`、`cloud/practice.mjs`）：

- 例如把 `await fetch(path,` 替换为带前缀的版本；
- 用 `replaceRequired()` 删除某个 `import`；
- 替换外观默认值等。

找不到被替换的原文时就报错，提示要求重新生成快照。

这种方式的问题是：每次 Web 前端有改动，补丁就可能失效；补丁散落在后端代码中，很难看懂前端最终运行的到底是什么代码；也没办法对补丁后的前端做正常的代码审查和测试。

## 决策驱动因素

1. **不重做：** 尽量保留现有界面与交互，把精力放在后端。
2. **可维护：** 前端最终运行的代码，应该就是仓库里看得到的代码，可以审查、可以测试。
3. **能跟上本地版：** Windows / 本地 Web 版会先实现新功能（需求 FR-07），在线版要有办法把这些功能带过来。
4. **契约不变：** 拓展 iframe 的 Bridge 协议（C-02）保持不变，旧拓展可以直接运行。
5. **不影响另一位开发者：** `quizforge_web` 仍在维护中，V2 的改造不应强迫它同步修改。

## 备选方案

### 方案 A：用 Vue / React 重写前端

- 优点：组件化，工程化程度更高，也有学习价值。
- 缺点：工作量最大，与“不重做”的要求直接冲突；手写白板、富文本、拓展宿主等复杂交互需要重新实现和测试。**排除。**

### 方案 B：沿用旧 Hub 的运行时补丁方式

- 优点：前端源码完全不动，`quizforge_web` 更新后理论上可以直接取用。
- 缺点：即上文的反面经验。补丁很脆弱，不可审查、不可测试。**排除。**

### 方案 C：把前端源码分叉（复制）到 V2 仓库，直接修改源码

在 V2 仓库中放入 `quizforge_web/core/web`（以及需要的 `core/shared`）在某个提交时的副本，记录来源提交号，然后像普通代码一样直接修改。

- 优点：
  - 运行的代码就是仓库里的代码，可以审查、测试和调试。
  - 改造不受 `quizforge_web` 约束，也不影响它。
  - 实现简单，可以立即开始。
- 缺点：
  - 两份前端代码会逐渐分化。本地版的新功能需要**手动移植**到 V2，移植成本随分化程度增加。

### 方案 D：抽出公共前端包，本地版与在线版共用

把前端改造成一个可配置的公共模块，通过“平台适配层”区分本地和在线（例如 `platform.local.js` / `platform.online.js`），两个产品引用同一份代码。

- 优点：长期来看只维护一份前端，新功能两边同时获得。
- 缺点：需要先大幅改造 `quizforge_web`，需要另一位开发者配合，而且会影响 Windows 版的发布节奏；当前阶段协调成本过高。

## 决策

**现在采用方案 C：将旧前端以源码分叉的方式放入 V2 仓库并直接改造。方案 D 作为以后的演进方向。**

方案 C 能马上开始，并且彻底避免了运行时补丁的问题。分化带来的移植成本，用下面的“上游同步流程”来控制。等在线版稳定、两边的差异明确之后，再评估是否值得走向方案 D（届时另写 ADR）。

### 设计要点

**1. 目录与来源记录**

```text
quizforge-v2/
└── frontend/
    ├── practice/          来自 quizforge_web/core/web
    ├── shared/            来自 quizforge_web/core/shared（richtext、answer-area、ink 等）
    ├── hub/               来自 quizforge_hub 的 java-hub static 页面
    └── UPSTREAM.md        记录每部分的来源仓库、提交号和分叉日期
```

**2. 改造范围（集中、可列清单）**

| 改造 | 内容 |
| --- | --- |
| 接口适配 | 只修改 `shared/api.js`：去掉 `X-QuizForge-Token`，改用 Cookie（ADR-005）；沿用旧接口已有的 `requestId`（幂等）与 `revision`（乐观锁）字段；统一处理 401、409 冲突等错误 |
| 删除本地功能 | 网络连接设置、开发者设置、本机 AI 配置、本机登录窗口、**题目编辑器**（在线版不提供编辑，需求第 5 节）、**拓展示例入口**（在线版不展示示例题库）等 |
| 增加在线功能 | 与 Hub 页面之间的导航、用户中心入口、AI 辅导侧边栏（FR-08） |
| 听力播放 | 由“`fetch` 整个文件后生成 Blob URL”改为直接 `<audio src>`（Cookie 认证后可行），支持流式播放与 Range（ADR-007） |
| 拓展宿主 | Bridge 协议与 iframe 沙箱方式（`srcdoc` + `sandbox="allow-scripts"`）均不变，见[遗留契约 C-02](../legacy/01-contracts.md) |

**3. 后端接口策略**

- 前端调用的接口以旧 `API.md` 的 HTTP 契约为**起点**，由 Java 后端重新实现。
- 旧接口在协议层面已经具备乐观锁（`revision`）、幂等（`requestId` 与请求回执）和条件读取（`stamp`），多用户问题出在底层的文件存储，而非接口设计（见[遗留契约 F-01](../legacy/01-contracts.md)）。因此 V2 **尽量保持这些接口的语义不变**，只在确有必要时前后端一起修改，并记录在接口文档中。
- 前端需要的完整接口清单，在“遗留契约清单”和详细设计阶段整理。

**4. 上游同步流程**

当 `quizforge_web` 新增了在线版也需要的功能时：

1. 在 V2 中开一个 Issue，注明上游提交号和功能说明。
2. 将相关改动手动移植到 `frontend/`，涉及的后端接口同步实现。
3. PR 中引用上游提交号，合并后更新 `UPSTREAM.md`。

**5. 构建与部署**

- 页面仍不需要构建，由 Nginx 直接作为静态文件提供，静态资源设置长期缓存（文件名带内容哈希或带版本参数）。
- 富文本组件沿用原来的打包脚本，打包产物纳入构建流程。

## 后果

**正面：**

- 不用重做界面，精力集中在后端和多用户问题上。
- 前端代码透明，可以审查和测试，告别运行时补丁。
- 旧拓展可以直接运行。

**负面：**

- 前端不使用现代框架，前端部分的“技术栈亮点”有限；简历与面试的重点放在后端和架构上。
- 与本地版的前端会逐渐分化，需要靠上游同步流程持续投入。
- 原生 JS 没有类型检查，改造时更依赖测试。

## 如何验证

1. **端到端测试：** 用 Playwright 在真实浏览器中自动化测试核心流程：登录、导入题库、作答、保存、提交、重做、查看历史、考试。每个 PR 都运行。这同时满足 NFR-09 中真实浏览器验证的部分要求。
2. **拓展兼容测试：** 使用旧版的全部基础题型和已发布题库中的拓展，验证它们在 V2 中能够渲染、保存、提交（验收场景 6、10）。
3. **无遗留检查：** 在 CI 中检查 `frontend/` 中不再出现 `X-QuizForge-Token`、网络设置等本地专用代码。
4. **移动端检查：** 在手机浏览器中人工验证白板手写、触控和布局（验收场景 9）。

## 面试要点（自用）

- 为什么不重写前端：瓶颈在后端，重写前端不能解决多用户问题，投入产出比低。
- 为什么不用运行时补丁：能说出旧系统的具体问题（不可审查、不可测试、上游一改就失效）。
- 源码分叉与公共包的取舍：短期可行性与长期维护成本之间的权衡，以及何时转向公共包。
- 前后端契约：为什么前端调用的接口要以文档化的契约为准，并且由前后端一起演进。
