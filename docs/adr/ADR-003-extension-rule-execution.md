# ADR-003：拓展评分规则的服务端执行方式

- 状态：提议
- 日期：2026-10-27
- 相关需求：C-03、C-04（[需求 1.3 节](../requirements/01-requirements.md)）、FR-04、FR-05、NFR-02、NFR-03
- 相关文档：[总体架构 4.7 节](../architecture/01-overview.md)

## 背景

QuizForge 的每种题型由一个拓展提供。拓展除了浏览器里的界面，还带一个**规则脚本**（JavaScript），通过 `QF.defineType({...})` 注册以下钩子：

| 钩子 | 作用 | 何时调用 |
| --- | --- | --- |
| `project(data, state)` | 把题目原始数据转成“给前端看的版本”（例如去掉标准答案） | 每次读题 |
| `validateQuestion` / `validateAnswer` | 校验题目和作答的格式 | 导入题库、保存作答 |
| `grade(data, answer)` | 评分，返回 `{score, maxScore, correct, feedback}` | 提交 |
| `getScore`、`getOutlineItems`、`review`、`prepareAiGrading` 等 | 小题状态、人工复核、AI 评分准备 | 按需 |

拓展还附带 JSON Schema（`questionSchema`、`answerSchema`），由 AJV 校验。

需求要求**评分必须在服务端可信执行**（FR-05），且**与本地版结果一致**（C-03）。这些规则是 JavaScript，而 V2 后端是 Java，所以必须决定：服务端在哪里、用什么引擎执行这些 JS。

### 旧系统怎么做的（仅作参考，不复用代码）

查阅 `quizforge_web/core/server/host/extensions/rule-engine.js` 与 `server/rules-runner.cjs`（@ `4522bb8`）：

- 规则在独立的 Node 子进程中运行，启动参数为 `--max-old-space-size=96`、`--disable-proto=throw`，并启用 Node 权限模型，只允许读取规则文件和 Schema。
- 子进程里，每个请求新建一个 `vm` 上下文：全局对象为空（`Object.create(null)`），禁止 `eval` 和 WebAssembly，每次钩子调用限时 650 ms，整个请求限时 8 s。
- 规则拿不到任何 Node API（没有 `require`、文件、网络），**本质上是纯函数**：输入 JSON，输出 JSON。
- 子进程按拓展分池复用，每个拓展最多 2～3 个，全局最多 12 个；空闲 60 秒或处理 500 次后回收。
- 输入上限 8 MB，单个规则文件上限 1 MB。

“规则是纯函数”这一点决定了它可以放在一个**无状态**的组件里执行，这是本决策的基础。

## 决策驱动因素

按重要性排序：

1. **结果一致性（C-03）：** 同一题、同一作答，在线评分必须与 Windows 本地版完全一致。本地版用的是 Node（V8 引擎）。
2. **安全隔离：** 拓展代码由第三方编写，即使已审核也视为不可信。它不能读到其他用户的数据、服务器文件、密钥，不能耗尽 CPU 或内存拖垮整个系统。
3. **故障隔离：** 规则卡死或崩溃，不能影响保存草稿、读历史等其他功能。
4. **性能：** 读题 P95 ≤ 500 ms、保存 P95 ≤ 1000 ms（NFR-02/03）。规则执行占用的时间要远小于这个预算。
5. **工程复杂度与学习价值：** 你主要用 Java，组件越少越容易维护；同时希望设计经得起面试追问。

## 备选方案

### 方案 A：独立的 Node 规则执行服务（rule-runner）

一个只做一件事的小型 Node 服务，Java 通过内网 HTTP 调用它。服务内部维护一个工作进程池，每个请求在全新的 `vm` 上下文中执行规则，外层套 Node 权限模型和内存上限，做法与旧系统相同，但代码重新编写。

- 优点：
  - 与本地版同为 V8 引擎、同一套 AJV，**一致性最有保证**。
  - 进程级隔离：规则崩溃或超时只影响一个工作进程，Java 进程完全不受影响。
  - 无状态，可单独重启、单独限流，以后可单独扩容。
- 缺点：
  - 多一个服务、一种语言，需要多部署和监控一个组件。
  - 每次调用多一次内网 HTTP 往返（本机约 1 ms 量级，需实测）。
  - 拓展文件需要能被它读到（共享只读目录）。

### 方案 B：Java 内嵌 GraalJS（GraalVM Polyglot）

在 Java 进程内用 GraalJS 执行规则，不需要额外服务。

- 优点：
  - 单一技术栈、单一进程，部署最简单。
  - 没有网络往返。
- 缺点：
  - **引擎不同（GraalJS 而非 V8）。** 规则的大部分行为相同，但数字格式化、正则、`Intl`、`Date` 等细节可能存在差异，难以保证与本地版逐位一致，需要大量对比测试来证明。
  - **Schema 校验也要换。** AJV 是 JS 库，要么在 GraalJS 里运行 AJV，要么改用 Java 的 JSON Schema 库；后者的校验语义可能与 AJV 不同。
  - **隔离强度依赖发行版。** 能限制 CPU、内存的强沙箱策略需要特定的 GraalVM 发行版和配置，许可与可用性需要另行核实（**待验证**）；在普通配置下，规则与 Java 业务共享同一个堆和进程，规则的内存问题可能影响整个应用。
  - 学习曲线较陡，相关资料少于 Node。

### 方案 C：Java 直接管理 Node 子进程（无独立服务）

Java 进程自己启动 Node 子进程，通过标准输入输出通信，即旧系统模式的 Java 版本。

- 优点：没有额外的网络服务；一致性与方案 A 相同。
- 缺点：进程池、超时、回收、崩溃重启这些逻辑全部要用 Java 写，而且与业务代码在同一个应用里，复杂度不比方案 A 低；Java 应用的运行环境必须同时装 Node，无法独立重启或扩容规则执行部分。

### 方案 D：不执行拓展 JS，把评分逻辑改写为 Java

- 违反 C-03：每新增一个题型都要改平台代码，Windows 版先行的新题型无法直接上线，与题型拓展系统的设计初衷（FR-05“新题型尽量通过插件接入”）相反。**直接排除。**

### 对比

| 维度 | A 独立 Node 服务 | B GraalJS 内嵌 | C Java 管子进程 |
| --- | --- | --- | --- |
| 与本地版一致 | 最好（同引擎） | 需大量对比测试 | 最好 |
| 安全隔离 | 进程级 | 依赖发行版与配置 | 进程级 |
| 故障不影响 Java | 是 | 否（同进程） | 基本是 |
| 部署组件数 | +1 | 0 | 0（但需装 Node） |
| 实现复杂度 | 中 | 中，且风险不确定 | 中偏高 |
| 可独立扩容 | 是 | 否 | 否 |

## 决策

**采用方案 A：独立的 Node 规则执行服务（rule-runner）。**

理由：一致性（驱动因素 1）和隔离（驱动因素 2、3）是硬性要求，方案 A 在这两点上最可靠；它付出的代价（多一个组件、一次内网往返）是可预期、可测量的。方案 B 的风险是不确定的，难以在合理时间内证明它满足 C-03。

### 设计要点

1. **职责单一、无状态。** rule-runner 只接受“执行规则”请求，不访问数据库，不知道用户是谁，不保存任何数据。
2. **调用协议（详细设计阶段定稿）：** Java → `POST /v1/execute`，请求体包含：
   - 拓展包标识：内容摘要 `digest`，以及 API 版本；
   - 操作：`project` / `validateQuestion` / `validateAnswer` / `grade` 等；
   - 题目数据、作答等输入 JSON。

   返回结果 JSON，或明确的错误码（`RULE_TIMEOUT`、`RULE_REJECTED`、`RULE_UNAVAILABLE` 等）。
3. **只执行已审核代码（C-04）：** 由 Java 负责检查摘要是否在白名单中；rule-runner 读取规则文件时再校验一次摘要，二者都通过才执行。拓展包放在共享存储中，rule-runner 以**只读**方式挂载。
4. **三层隔离：**
   - 进程：工作进程有内存上限，启用 Node 权限模型，只能读本拓展的规则和 Schema 文件，没有网络权限，环境变量清空；
   - 上下文：每个请求新建 `vm` 上下文，空全局对象，禁止 `eval` 和 WebAssembly；
   - 时间：单次钩子调用和整个请求都有超时，超时则杀掉该工作进程。
5. **容量控制：** 工作进程总数按 CPU 核数配置；请求排队有上限，超出时快速返回 503，而不是无限等待。
6. **网络位置：** 只监听内网或 Docker 内部网络，不对外暴露。
7. **代码重写：** 按需求“不复用旧源码”，rule-runner 重新编写；旧的 `rules-runner.cjs` 只用作对照，其行为作为一致性测试的参照标准。

### Java 侧如何减少调用和应对故障

- **读题投影缓存：** 未提交状态下 `project` 的结果只取决于“题目数据 + 拓展摘要”，可以缓存（缓存键 = 题目内容哈希 + 拓展摘要）。这样大部分读题请求不调用 rule-runner。
- **超时与降级：**
  - Java 调用 rule-runner 设置连接和读取超时（初值 2 s / 10 s，压测后调整）。
  - rule-runner 不可用时，**保存草稿不受影响**，因为保存草稿只做 Schema 校验和落库，是否需要调用规则在详细设计中确认；正式提交返回明确错误，提示稍后重试，作答内容已保存。
- **独立连接池：** Java 调用 rule-runner 使用单独的 HTTP 连接池和并发上限，规则变慢时不会占满处理其他请求的线程。

## 后果

**正面：**

- 评分语义与本地版保持一致，现有题型可直接上线。
- 拓展代码的任何故障被限制在 rule-runner 的一个工作进程内。
- rule-runner 无状态，可以随时重启；需要时可单独部署到另一台机器。

**负面（需要承担的成本）：**

- 系统里有两种语言。你需要掌握 Node 的基础，以及 `vm`、子进程和权限模型。
- 多一个部署和监控对象（Docker Compose 里多一个容器）。
- Java 与 rule-runner 之间的接口要版本化管理，两边改动要同步。
- 拓展包存储必须让两个服务都能访问（共享只读卷）。

**风险：**

- `vm` 模块本身不是安全边界，Node 官方文档明确说明不应用它运行不可信代码。因此必须同时依赖**进程级隔离 + 权限模型 + 内存与时间限制 + 审核白名单**，不能只靠 `vm`。
- 若压测显示 rule-runner 成为瓶颈，可以先增加工作进程、扩大缓存，再考虑拆到独立机器。

## 如何验证

1. **一致性测试：** 收集现有全部基础题型和已发布题库中的拓展，构造“题目 + 作答”样本，分别交给旧 `rules-runner.cjs` 和新 rule-runner，输出必须逐字段一致。该测试进入 CI。
2. **隔离测试：** 编写恶意规则样本，包括死循环、无限分配内存、尝试 `require('fs')`、访问 `process`、原型污染、超大输出。每种样本都必须被拒绝或超时终止，rule-runner 和 Java 应用都持续可用。
3. **故障测试：** 压测过程中手动杀掉 rule-runner，验证：保存草稿仍然成功；提交返回可理解的错误；rule-runner 恢复后自动继续工作。
4. **性能测试：** 单独压测 rule-runner，记录 `grade` 和 `project` 的 P95；在 100 人混合场景中，统计其耗时在保存 P95 中所占比例，并记录读题时投影缓存的命中率。

## 面试要点（自用）

- 为什么不用 GraalJS：一致性无法低成本证明，隔离强度依赖发行版。这是一次有依据的取舍，不是不了解这项技术。
- 为什么 `vm` 不够：它不是安全边界，所以要多层隔离。
- 为什么 rule-runner 设计成无状态：可以随时重启、可以扩容，故障也不会扩散。
- 投影缓存为什么成立：`project` 是纯函数，输入相同则输出相同。
