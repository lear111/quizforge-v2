# ADR-010：RabbitMQ 处理 AI 评分与通知任务，配合事务发件箱

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-08（AI 评分不影响刷题）、考试模式（交卷后批量评分）、FR-02（审核通知）、需求第 5 节
- 相关决策：[ADR-001](ADR-001-modular-monolith.md)、[ADR-002](ADR-002-database-mysql.md)

## 背景

有两类工作**不应该在用户请求中同步完成**：

1. **AI 自动评分。** 主观题提交后，或考试交卷后（一次交卷可能有几十道主观题），需要调用大模型评分。特点：
   - 慢：每次数秒到数十秒；
   - 会失败：超时、限流、上游故障，需要重试；
   - 有突发：考试截止时，很多人同时交卷；
   - 结果要写回作答状态与历史，而且**不能用过期的结果覆盖新结果**（数据库中已有 `grading_generation` 字段用于判断）。
2. **通知邮件。** 例如题库审核结果。旧系统为此专门实现了一个“持久化合并队列 + 失败重试 + 发送额度”的机制（`docs/JAVA_ADMIN_AI_PRACTICE.md`）。

旧系统把这两件事都做成了**自己实现的持久化队列**，包括 AI 评分任务的文件（`.state/ai-grading/`）和审核邮件队列表。重试、失败处理、并发控制都要自己写。

## 决策驱动因素

1. **请求快速返回：** 提交、交卷接口不等待模型评分。
2. **可靠：** 评分任务不能因为应用重启而丢失；失败要重试；多次失败后要能被人工发现和处理。
3. **削峰：** 考试截止时的批量评分要按可控的速度消费，不能把上游模型或自己的线程池压垮。
4. **一致性：** “提交成功”与“评分任务已登记”必须同时成立，不能出现提交成功但任务丢失。
5. **与规模相称。**

## 备选方案

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 应用内线程池异步执行 | `@Async` / `CompletableFuture` | 简单，但应用重启时任务丢失，没有持久化与重试。**不满足驱动因素 2** |
| B. 数据库任务表 + 定时轮询 | 任务写表，后台定时领取（`SELECT ... FOR UPDATE SKIP LOCKED`） | 可靠且无新组件；但重试退避、死信、并发消费数、削峰都要自己实现，与旧系统一样“自己造队列” |
| C. RabbitMQ | 任务作为消息投递，消费者确认、失败重试、死信队列、预取数量（prefetch）控制并发 | 重试、死信、限速都是现成能力；多一个组件 |

方案 B 在当前规模下也能工作。选择 C 的理由是：重试与死信是这两类任务的**核心需求**，而不是附加功能，用成熟组件实现比自己维护更可靠；同时把“任务的可靠登记”（数据库）和“任务的调度执行”（消息队列）清楚地分开。

## 决策

**采用方案 C：引入 RabbitMQ，用于 AI 评分任务与通知任务；并使用事务发件箱（Transactional Outbox）保证“业务数据提交”与“消息发出”的一致性。**

### 为什么需要事务发件箱

直接在业务代码中“先提交数据库，再发消息”有两种失败情况：

- 数据库提交成功，发消息前应用崩溃 → **任务丢失**，主观题永远停在“待评分”；
- 先发消息，数据库事务却回滚 → 消费者去评分一道并不存在的提交。

**做法：**

```text
提交请求的事务内：
  ① 更新作答状态（grading_status = pending）
  ② INSERT INTO outbox_message(...)        —— 与 ① 在同一个事务中，要么都成功，要么都失败
事务提交后：
  ③ 发件箱投递器读取未投递的消息 → 发送到 RabbitMQ → 收到 publisher confirm 后标记为已投递
```

投递器可能因为崩溃而重复发送同一条消息，所以**消费者必须幂等**（见下文）。这就是“至少一次投递 + 幂等消费 = 效果上恰好一次”。

### 消息与队列

| 队列 | 消息 | 消费者 | 并发与重试 |
| --- | --- | --- | --- |
| `ai.grading` | `{messageId, userId, contextId, questionId, gradingGeneration}` | AI 评分：调用 rule-runner 的 `prepareAiGrading` → 调用模型（Structured Output 返回分数与评语）→ rule-runner 的 `review` → 写回 | `prefetch` 限制并发（初值 4）；失败按 10s、60s、5min 退避重试 3 次；仍失败进入死信队列 `ai.grading.dlq`，作答保持“待评分”，用户可手动重试或人工评分 |
| `notify.email` | `{messageId, template, to, params}` | 邮件发送 | 失败重试；超过次数进入死信；保留旧系统的发送额度限制 |

消息只携带标识，**不携带题目和作答内容**：消费者从数据库读取最新数据。这样消息很小，也不会把私人数据复制到队列中。

### 消费者幂等

- 每条消息有唯一的 `messageId`；消费成功后写入 `mq_consumed(message_id)` 表（主键去重），与写回评分结果在**同一个事务**中。
- 写回 AI 评分时再检查 `grading_generation`：若作答已被重做或重新提交（代数已变），丢弃这次过期的结果。这一点旧系统已有，V2 保留。

### 新增表（数据库设计后续版本）

```sql
CREATE TABLE outbox_message (
  id            CHAR(36)     NOT NULL,
  topic         VARCHAR(64)  NOT NULL,      -- ai.grading / notify.email
  payload       JSON         NOT NULL,
  created_at    DATETIME(3)  NOT NULL,
  published_at  DATETIME(3)  NULL,
  attempts      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  KEY idx_outbox_pending (published_at, created_at)
);

CREATE TABLE mq_consumed (
  message_id   CHAR(36)     NOT NULL,
  consumer     VARCHAR(64)  NOT NULL,
  consumed_at  DATETIME(3)  NOT NULL,
  PRIMARY KEY (message_id, consumer)
);
```

### 不用 RabbitMQ 的地方

| 不用于 | 原因 |
| --- | --- |
| 保存作答、提交本身 | 必须同步确认持久化（NFR-05），用户需要立即知道结果 |
| 题库版本更新 | 采用懒更新，每个用户打开时在自己的小事务中完成（题库共享与版本更新设计第 3 节），不需要批量异步 |
| AI 辅导问答 | 用户正在等待回答，使用流式响应同步返回；只把**自动评分**做成异步任务 |
| 模块之间的普通调用 | 模块化单体内直接调用接口（ADR-001），不用消息解耦 |

### 可用性与降级

RabbitMQ 不可用时：提交与交卷**照常成功**，因为任务已经安全地登记在 `outbox_message` 中；投递器持续重试，RabbitMQ 恢复后任务自动送达。用户看到的只是“评分中”的时间变长。

## 后果

**正面：**

- 提交、交卷快速返回；评分任务可靠、可重试、失败可见。
- 考试截止的评分高峰被平滑为可控速度。
- 事务发件箱与幂等消费保证了“不丢、不重复生效”。

**负面：**

- 多一个组件，需要部署和监控（队列长度、死信数量）。
- 引入了“最终一致”：提交后评分结果需要稍后才出现，前端要展示“评分中”并定时刷新（旧前端已有待评分状态，可复用）。
- 多了投递器、幂等表、死信处理等代码与测试。

## 如何验证

1. **不丢任务：** 提交主观题后立即杀掉应用；重启后评分任务仍被投递并完成。
2. **不重复生效：** 让投递器重复发送同一消息，评分只写入一次。
3. **过期结果：** 评分进行中用户重做该题，旧的评分结果被丢弃。
4. **削峰：** 模拟 100 人同时交卷，队列积压后按 `prefetch` 速度消费，刷题接口的 P95 不受影响。
5. **降级：** 停掉 RabbitMQ 时提交仍成功；恢复后任务自动送达。
6. **死信：** 让模型持续失败，任务在重试后进入死信队列，作答保持“待评分”，可手动重试。

## 面试要点（自用）

- 为什么用消息队列而不是 `@Async`：持久化、重试、死信、削峰。
- **事务发件箱**解决什么问题：数据库与消息之间没有分布式事务，如何做到不丢、不错发。
- 至少一次投递 + 幂等消费；`messageId` 去重表与业务写入在同一事务中的原因。
- publisher confirm、消费者手动 ack、prefetch 分别控制什么。
- 为什么消息里不放业务数据：数据可能已过期；避免把私人数据复制到队列中。
- 为什么方案 B（数据库任务表）也可行，以及什么情况下会选它。
