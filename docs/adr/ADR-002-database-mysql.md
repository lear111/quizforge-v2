# ADR-002：业务数据使用 MySQL 8

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-03、FR-04、FR-09、NFR-05、NFR-06、NFR-11
- 相关文档：[总体架构 4.5 节](../architecture/01-overview.md)

## 背景

V2 需要持久化的业务数据包括：用户与权限、题库目录与版本、个人题库实例、题目数据、作答与草稿、提交与评分、考试、历史快照、审核记录、AI 用量与余额。

旧系统的做法（已由源码证实）：

- Java Hub 使用 SQLite（`data-java/hub.sqlite`），用原生 JDBC 访问。
- Node 练习服务另有一个 SQLite，记录配额和导入信息。
- **作答、草稿、历史等核心练习数据不在数据库里**，而是保存在每个用户工作区目录下的 JSON 文件中。为了保证写入不出错，旧系统只能让所有请求排队，并在每次请求前复制整个工作区作为备份。

需要决定 V2 用什么存储这些数据。图片、音频、手写图等二进制文件不在本 ADR 范围内，统一放文件存储（见 ADR-007）。

## 决策驱动因素

1. **并发写入的正确性：** 不同用户同时保存时互不阻塞；同一用户多标签页同时保存时，能检测冲突，不会静默覆盖（FR-04）。
2. **可靠持久化：** 只有在事务提交后才确认保存成功，进程崩溃后已确认的数据不丢（NFR-05）。
3. **数据隔离：** 每次查询都能方便地按用户过滤，防止跨用户读取（NFR-06）。
4. **可运维：** 有成熟的备份、恢复、监控和版本迁移工具（NFR-11）。
5. **支持以后启动多个应用实例：** 数据库可以通过网络被多个 Java 进程访问（ADR-001 的无状态要求）。
6. **学习与面试价值：** 国内 Java 后端岗位几乎都考察 MySQL（InnoDB、索引、事务隔离、MVCC、锁）。

## 备选方案

### 方案 A：继续使用 SQLite 加 JSON 文件（旧方式）

- 优点：零运维，不需要单独的数据库服务；旧数据迁移最简单。
- 缺点：
  - JSON 文件没有事务，正是旧系统需要全局排队和整份备份的根本原因。
  - 即使把练习数据全部放进 SQLite，**同一时刻也只能有一个写事务**（WAL 模式允许多个读者，但只允许一个写者）。说实话，按估算的每秒约 10 次写入，SQLite 很可能也能承受，所以**性能并不是排除它的主要理由**。
  - 真正的问题是：数据库文件只能被同一台机器上的进程访问，无法支持多个应用实例；缺少成熟的在线备份、监控和权限管理工具；面试价值低。

### 方案 B：MySQL 8（InnoDB）

- 优点：
  - 行级锁加 MVCC：不同用户写不同的行，彼此不阻塞。
  - 事务、崩溃恢复（redo log）成熟可靠。
  - 生态完善：Spring Boot、HikariCP、MyBatis/JPA、Flyway 都对它有一流支持；备份工具（`mysqldump`、XtraBackup）、主从复制都很成熟。
  - 是国内招聘中最常考察的数据库，需求文档也将它列为候选。
  - 支持 `JSON` 列类型，适合存放结构由拓展决定的题目数据和作答数据。
- 缺点：
  - 多一个需要运维的服务（安装、配置、备份）。
  - JSON 支持不如 PostgreSQL 的 `JSONB` 强大（索引和查询能力较弱）。
  - 默认隔离级别是“可重复读”，加上间隙锁，行为比较复杂，需要专门理解。

### 方案 C：PostgreSQL

- 优点：功能上与 MySQL 相当甚至更强，`JSONB` 支持更好，SQL 标准更完整，事务语义更直观。
- 缺点：国内 Java 后端岗位的考察重点不在它；MyBatis 等工具的国内资料以 MySQL 为主；对本项目而言，`JSONB` 的优势用处有限，因为我们**不打算对题目内部的 JSON 字段做复杂查询**（题目内容由拓展解释，平台只整体读写）。

### 方案 D：MongoDB 等文档数据库

- 优点：题目和作答本来就是 JSON，存储天然契合。
- 缺点：用户、题库、作答、历史之间是明显的关系型数据，需要外键约束和多表事务；数据迁移和一致性设计会更复杂；与目标岗位的技术栈匹配度低。

## 决策

**采用方案 B：MySQL 8（InnoDB）**，版本使用 8.4 LTS（具体小版本在搭建开发环境时确认）。

说明：PostgreSQL 在技术上同样完全可以胜任。选择 MySQL 主要基于**生态、学习和求职目标**，这是一次有意识的权衡，不是因为 PostgreSQL 做不到。

### 设计约定（详细设计阶段细化）

| 约定 | 内容 | 原因 |
| --- | --- | --- |
| 存储引擎 | InnoDB | 事务、行锁、崩溃恢复 |
| 字符集 | `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci` | 支持中文、公式符号与 emoji |
| 结构管理 | 用 Flyway 管理表结构变更，所有变更写成版本化 SQL 脚本，纳入 Git | 可追溯、可重复、可回滚（NFR-11） |
| 连接池 | HikariCP（Spring Boot 默认），连接数初值约 20，压测后调整 | 连接数并非越多越好 |
| 题目 / 作答数据 | 平台关心的字段（ID、用户、状态、版本号、时间）用普通列并建索引；由拓展决定结构的内容放 `JSON` 列 | 平台按普通列查询，不解析 JSON 内部 |
| 并发冲突 | 作答等可能被同时修改的行带 `version` 列，用乐观锁更新：`UPDATE ... WHERE id=? AND version=?`，影响 0 行即冲突，返回 409 | 防止多标签页互相静默覆盖（FR-04） |
| 幂等 | 沿用旧接口的请求体字段 `requestId`（见[遗留契约 F-01](../legacy/01-contracts.md)），在回执表中对 `(user_id, request_id)` 建唯一约束；重放相同请求返回原结果 | 重试不会产生重复提交（验收场景 3） |
| 用户隔离 | 所有用户私有表都有 `user_id` 列，查询必须带上它；通过 Repository 层统一约束和测试保证 | 防止跨用户访问（NFR-06） |
| 大字段 | 手写图片、附件等二进制内容不存入 MySQL，表里只存文件引用 | 控制库大小，备份更快 |
| 隔离级别 | 在 READ COMMITTED 与默认的 REPEATABLE READ 之间选择，在详细设计中确定 | 需要结合具体的读写模式分析 |

## 后果

**正面：**

- 从根本上消除了旧系统的全局排队和整份备份：保存一题就是更新一行。
- 冲突检测、幂等、用户隔离都可以用标准的数据库手段实现，并且容易测试。
- 应用可以无状态，支持以后启动多个实例。

**负面：**

- 部署中多一个 MySQL 容器，需要配置备份（至少每日全量备份，详见运维设计），并定期演练恢复。
- 迁移工具需要把旧的 SQLite 数据和 JSON 文件转换为新的表结构，工作量不小（FR-09，ADR-008）。
- 开发和测试环境都需要 MySQL；集成测试使用 Testcontainers 启动真实的 MySQL，不用 H2 等内存数据库代替，以免两者行为不一致。

## 如何验证

1. **并发写测试：** 100 个虚拟用户同时保存各自的作答，没有请求因等待锁而超时；P95 满足 NFR-03。
2. **冲突测试：** 同一用户两个会话用相同版本号同时保存同一题，恰好一个成功，另一个得到 409，数据库中没有被覆盖的数据。
3. **幂等测试：** 同一 `requestId` 的提交重放 10 次，只产生一条提交记录，且每次返回相同结果；同一 `requestId` 搭配不同内容时被拒绝。
4. **崩溃测试：** 在保存过程中强制杀掉 Java 进程和 MySQL 容器，重启后所有已返回成功的保存都存在。
5. **备份恢复演练：** 从备份恢复到一个新实例，数据条数与摘要和原库一致。

## 面试要点（自用）

- 为什么不用 SQLite：不是因为性能不够，而是因为只能单写者、不能被多个实例访问，运维能力也弱。不要说“SQLite 扛不住 100 人”，这个说法不准确。
- 为什么不用 PostgreSQL：两者都可以，选 MySQL 是基于生态和团队技能的取舍。
- 乐观锁与悲观锁：这里为什么用乐观锁（冲突少、不长时间持锁），以及什么时候应该用 `SELECT ... FOR UPDATE`。
- 题目数据为什么用 JSON 列：结构由拓展决定，平台不解析，只整体读写。
- 为什么集成测试不用 H2：方言和锁行为不同，测试通过不代表生产环境没问题。
