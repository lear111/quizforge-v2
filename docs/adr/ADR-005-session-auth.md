# ADR-005：浏览器使用服务端会话，设备使用不透明令牌

- 状态：提议
- 日期：2026-10-27
- 相关需求：FR-01、C-05、C-06、NFR-06、第 4 节安全约束
- 相关决策：[ADR-001](ADR-001-modular-monolith.md)（应用无状态）、[ADR-002](ADR-002-database-mysql.md)

## 背景

用户登录后，后续请求要能识别“这是谁”。需要决定登录状态如何保存和校验。

V2 有两类调用方：

1. **浏览器：** 用户在网页中使用 Hub 和练习空间，这是绝大多数请求的来源。
2. **设备客户端：** 已发布的 Windows / Android 客户端通过设备授权获得令牌，用 `Authorization: Bearer` 调用 Hub 的导入和 AI 接口（契约 C-05）。

旧系统（仅作参考）：

- 浏览器会话保存在 SQLite 的 `sessions` 表中，数据库只存令牌的 SHA-256 哈希，不存明文。
- 设备令牌保存在 `connect_devices` 表中，180 天不用自动失效，每个账号最多 10 台设备。
- 账号被封禁时，立即撤销该账号的所有会话和设备授权。
- 旧 Node 练习服务把自己的会话保存在**进程内存**中，重启后需要重新登录。这一点 V2 不能沿用（ADR-001 要求应用无状态）。

## 决策驱动因素

1. **能够立即撤销：** 封禁账号、修改密码、用户主动退出后，原来的登录状态必须立即失效。
2. **应用无状态：** 登录状态不能保存在 Java 进程内存中，重启后用户不应掉线，以后也要能运行多个实例。
3. **安全：** 防止令牌被窃取后长期有效，防止跨站请求伪造（CSRF），防止题型拓展的 iframe 读取登录凭证。
4. **兼容已发布客户端（C-05）：** 设备令牌的使用方式保持不变。
5. **简单，而且能讲清楚：** 方案要容易实现、容易测试，面试时能说清楚为什么这样选。

## 备选方案

### 方案 A：服务端会话（Cookie 中存随机令牌，数据库中存会话记录）

登录成功后生成一个随机令牌，放进 `HttpOnly`、`Secure`、`SameSite` 的 Cookie 中；数据库保存令牌的哈希、用户 ID 和过期时间。每个请求根据 Cookie 查一次会话表。

- 优点：
  - 删除会话记录即可**立即撤销**。
  - 浏览器脚本读不到 `HttpOnly` Cookie，可以降低 XSS 窃取令牌的风险。
  - 数据库只存哈希，即使数据库泄露也无法直接冒充用户。
  - 会话存在 MySQL 中，应用本身无状态。
- 缺点：
  - 每个请求都要查一次数据库。按索引查询一行，在 100 人规模下开销很小，必要时可以加短时缓存。
  - 使用 Cookie 需要防范 CSRF。

### 方案 B：Spring Session JDBC

由 Spring Session 把 `HttpSession` 存入数据库表，效果与方案 A 类似。

- 优点：Spring 官方组件，配置简单，可以直接使用 `HttpSession`。
- 缺点：
  - 会话 ID 以明文作为主键存储，不满足“只存哈希”的要求。
  - `HttpSession` 鼓励在会话中存放各种数据，这些数据在每个请求中都要序列化和反序列化。
  - 表结构和行为由框架决定，与设备令牌无法统一管理。

### 方案 C：JWT（无状态令牌）

登录后签发包含用户信息的签名令牌，服务器只验证签名，不查数据库。

- 优点：校验时不需要查询数据库；多个服务之间共享登录状态比较方便。
- 缺点：
  - **无法立即撤销。** 令牌在过期前一直有效。要支持封禁和退出，就必须维护一个黑名单并在每次请求时查询，这样又回到了查数据库，失去了“无状态”的意义。
  - 常见的补救办法是“短期访问令牌 + 刷新令牌”，但这显著增加了复杂度。
  - 如果存放在 `localStorage` 中，容易被 XSS 窃取。
  - 本项目是模块化单体，没有多个服务共享登录状态的需求，JWT 的主要优势用不上。

## 决策

**浏览器采用方案 A：自建服务端会话表，Cookie 中只存随机令牌，数据库中只存令牌的 SHA-256 哈希。设备客户端使用同样存储方式的不透明令牌（Bearer）。两者通过 Spring Security 统一接入。**

立即撤销和应用无状态是硬性要求，方案 A 能直接满足；方案 C 的主要优势在本项目中用不上，却带来了撤销难题。

### 设计要点（详细设计阶段细化）

**浏览器会话：**

| 项目 | 约定 |
| --- | --- |
| 令牌 | 256 位安全随机数，Base64URL 编码 |
| 存储 | 表 `auth_session`：令牌哈希（主键）、用户 ID、创建时间、最后使用时间、过期时间、客户端信息 |
| Cookie | `HttpOnly; Secure; SameSite=Lax; Path=/`；使用 `__Host-` 前缀，防止被子域名覆盖 |
| 有效期 | 闲置超时与绝对过期时间分别设置，具体数值在详细设计中确定 |
| 撤销 | 退出时删除当前会话；修改密码或封禁时删除该用户的全部会话 |
| 登录时 | 每次登录都生成新令牌，防止会话固定攻击 |

**CSRF 防护：**

- 使用 `SameSite=Lax` Cookie。
- 所有写操作（POST / PUT / DELETE）在服务端校验 `Origin` 请求头必须等于站点自身的来源，旧系统也是这样做的。
- 是否另加 CSRF Token，在详细设计中评估。

**题型拓展隔离：**

- 沿用旧前端的做法（已由源码证实，见[遗留契约 C-02](../legacy/01-contracts.md)）：拓展以 `srcdoc` 注入 `sandbox="allow-scripts"`（不含 `allow-same-origin`）的 iframe，运行在**不透明源**中，读不到主站 Cookie；iframe 的 CSP 为 `connect-src 'none'`，拓展也无法直接发起网络请求。拓展只能通过 Bridge 请求宿主代为操作。因此不需要为拓展另设子域名。

**设备令牌（C-05）：**

- 保持 `Authorization: Bearer <token>` 的调用方式，以及旧客户端的授权流程（授权码、S256 校验等）。授权流程的细节在遗留契约清单中整理。
- 存储在 `auth_device` 表中，同样只存令牌哈希；保留 180 天闲置失效和每个账号最多 10 台设备的规则。
- 设备令牌只能访问设备相关接口（导入、AI 网关），**不能**当作浏览器会话使用；反过来，浏览器 Cookie 也不能调用设备接口。
- 旧系统中设备令牌只存 SHA-256 哈希（格式 `qfd_<随机串>`，见[遗留契约 C-05](../legacy/01-contracts.md)），与本方案的存储方式一致，**可以直接迁移**，用户无需在客户端重新授权。

**实现方式：**

- 使用 Spring Security，编写自定义认证过滤器：从 Cookie 或 `Authorization` 头中取出令牌，计算哈希，查表得到用户，放入 `SecurityContext`。
- 登录密码沿用旧的 scrypt 格式校验（C-06）；新注册用户的密码哈希算法在详细设计中确定。

## 后果

**正面：**

- 封禁、退出、修改密码后立即生效。
- 应用重启不会导致用户掉线；需要时可以运行多个实例。
- 数据库泄露时，攻击者无法直接用会话表中的数据登录。
- 浏览器会话和设备令牌机制一致，易于理解和测试。

**负面：**

- 每个请求增加一次按主键的数据库查询。
- 需要自己编写和维护认证过滤器，而不是直接使用现成组件，所以对它的测试必须充分。
- 需要定期清理过期会话（定时任务）。

## 如何验证

1. **撤销测试：** 封禁用户后，该用户已登录的浏览器和设备的下一个请求都返回 401。
2. **重启测试：** 重启 Java 应用后，已登录用户无需重新登录。
3. **凭证隔离测试：** 设备令牌调用浏览器接口返回 401 或 403；浏览器 Cookie 调用设备接口返回 401 或 403。
4. **CSRF 测试：** 从其他来源发起的写请求被拒绝。
5. **拓展隔离测试：** 在拓展 iframe 中运行脚本，尝试读取 Cookie 或直接调用主站 API，均失败。
6. **兼容测试：** 使用已发布版本的 Windows 客户端完成一次设备授权和题库导入（验收场景 10）。
7. **性能检查：** 压测中统计会话查询的耗时，确认它在请求总耗时中占比很小。

## 面试要点（自用）

- Session 与 JWT 的取舍：核心在于能否立即撤销，而不是哪个更先进。
- “JWT 无状态”的代价：要支持撤销就需要黑名单，又变回了有状态。
- 为什么令牌只存哈希：数据库泄露也无法直接冒充用户，这与密码只存哈希是同一个道理。
- `HttpOnly`、`Secure`、`SameSite`、`__Host-` 分别防的是什么。
- 用 Cookie 为什么要防 CSRF，以及校验 `Origin` 头的作用。
- 第三方代码（拓展）为什么要运行在不透明源的沙箱 iframe 中，以及 `allow-scripts` 与 `allow-same-origin` 同时开启为什么危险。
